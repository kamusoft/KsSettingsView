4. tasks 6.3 — 要件未満・未設定でのガード (KSSV0001)
================================================================
4-a. 要件未満 (android=21 / ios=15.0)

$ dotnet build -c Release -f net10.0-android
  exit 1
  KSSV0001: KsSettingsView requires SupportedOSPlatformVersion 29 or later for
  net10.0-android (minimum supported: Android API 29, iOS 16.0), but the current
  value is '21.0'. Add <SupportedOSPlatformVersion>29</SupportedOSPlatformVersion>
  to a PropertyGroup for this target framework in your project file.
  XAAMM* の出現件数: 0

$ dotnet build -c Release -f net10.0-ios -p:RuntimeIdentifier=iossimulator-arm64
  exit 1
  KSSV0001: KsSettingsView requires SupportedOSPlatformVersion 16.0 or later for
  net10.0-ios (minimum supported: Android API 29, iOS 16.0), but the current
  value is '15.0'. Add <SupportedOSPlatformVersion>16.0</SupportedOSPlatformVersion>
  to a PropertyGroup for this target framework in your project file.

4-b. manifest merger より先に出ることの対照実験
     ガードの要件定数だけを外部から下げて (-p:KsSettingsViewMinAndroidApi=1)
     同じ android=21 の構成をビルドすると、ガードは沈黙し manifest merger が失敗する:

$ dotnet build -c Release -f net10.0-android -p:KsSettingsViewMinAndroidApi=1
  exit 1
  KSSV0001 の出現件数: 0
  XAAMM0000: .../AndroidManifest.xml:9:3-72 Error:
  XAAMM0000: 	uses-sdk:minSdkVersion 21 cannot be smaller than version 23 declared
             in library .../lp/152/jl/AndroidManifest.xml as the library might be
             using APIs not available in 21
  XAAMM0000: 	Suggestion: use a compatible library with a minSdk of at most 21,
  XAAMM0000: 		or increase this project's minSdk version to at least 23,

  => ガードが有効なときは KSSV0001 だけが出て XAAMM は 1 件も出ない
     (ビルドが CoreCompile の前で止まり manifest merger まで進まない)。
     ガードを外すと XAAMM0000 が出る。よってガードは manifest merger より先に働く。

4-c. 未設定 (csproj から SupportedOSPlatformVersion の行を削除)

  評価値 (dotnet msbuild -getProperty:SupportedOSPlatformVersion):
    net10.0-android => 21.0   (SDK 既定)
    net10.0-ios     => 26.5   (SDK 既定)

$ dotnet build -c Release -f net10.0-android
  exit 1 / KSSV0001 (current value is '21.0') / XAAMM* 0 件

  ※ .NET SDK は platform TFM に必ず既定値を与えるため、csproj から行を消しても
    SupportedOSPlatformVersion が空文字になる経路はなかった。Android は既定 21.0 が
    要件未満なのでガードが働く。iOS は既定 26.5 が要件を満たすためエラーにならない
    (ガードの意味論どおり — 要件を満たす場合は何も出さない)。
    空文字の分岐 ('$(SupportedOSPlatformVersion)' == '') は targets 側に実装されているが、
    通常の csproj 記述では到達しない。

6. 留意点 (spec との差)
================================================================
6-1. nuget.config に nuget.org を残した
  spec / tasks は「ローカルフィードだけを取得元にする」としているが、
  <clear/> と local-ksv だけの構成では dotnet new maui のテンプレート自体が
  restore できない (実測):
    error NU1101: パッケージ Xamarin.AndroidX.Lifecycle.LiveData が見つかりません。
    ソース <DOTNET_ROOT>/library-packs, local-ksv には、この ID のパッケージが存在しません。
    (Microsoft.Extensions.Hosting.Abstractions / Xamarin.Android.Glide /
     Xamarin.Google.Android.Material など 14 件が同様)
  MAUI の公開依存 (Xamarin.AndroidX.* / Microsoft.Extensions.*) は workload の
  library-packs に入らず nuget.org からしか取れないため、nuget.org を 1 件追加した。
  KsSettingsView の 3 パッケージがローカルフィードからだけ取得されたことは
  上記 1. の .nupkg.metadata の source で確認済み。

6-2. Android の消費者ビルドに XA4301 警告が 4 件出る
  4 件はいずれも同じ内容:
    obj/Release/net10.0-android/lp/254|255/jl/jni/{arm64-v8a,x86_64}/libandroidx.graphics.path.so :
    warning XA4301: APK には既に項目 lib/<abi>/libandroidx.graphics.path.so が含まれています; 無視しています。
  発生源は .NET Android SDK が assembly ごとに自動生成する aar 2 本:
    KsSettingsView.Maui.0.1.0-alpha.1.nupkg
      lib/net10.0-android36.0/KsSettingsView.Maui.aar
      -> jni/{armeabi-v7a,x86,arm64-v8a,x86_64}/libandroidx.graphics.path.so の 4 ファイルのみ
    KsSettingsView.Binding.Android.0.1.0-alpha.1.nupkg
      lib/net10.0-android36.0/KsSettingsView.Binding.Android.aar
      -> 同じ 4 ファイルのみ
  どちらも推移依存 androidx.graphics.path が既に APK に入れている .so の重複で、
  SDK 側が無視して続行するため成果物への影響はない (ビルドは成功する)。
  facade 側の aar は deviation.md で「本変更による混入ではない」と合意済みだが、
  消費者ビルドにこの警告が出ることは本検証で初めて観測した。
  spec は restore の警告 0 件を要求しており (満たしている)、ビルド警告 0 件は要求していない。

8. 名前衝突 (SwitchCell / EntryCell) の実測
================================================================
facade の名前空間 KsSettingsView と MAUI の暗黙 using を併用した C# コードでの
あいまい参照を、同じ消費者アプリ (MyApp) で両型・両 TFM について実測した。

8-a. 完全修飾も alias も使わない場合 (NameCollisionProbe.cs)

  using KsSettingsView;
  namespace MyApp;
  internal static class NameCollisionProbe
  {
      internal static void Use()
      {
          _ = new SwitchCell();
          _ = new EntryCell();
      }
  }

  $ dotnet build -c Debug -f net10.0-ios     -t:Compile   => 2 エラー
  $ dotnet build -c Debug -f net10.0-android -t:Compile   => 2 エラー

  NameCollisionProbe.cs(9,17): error CS0104: 'SwitchCell' は、
    'Microsoft.Maui.Controls.SwitchCell' と 'KsSettingsView.SwitchCell' 間のあいまいな参照です
  NameCollisionProbe.cs(10,17): error CS0104: 'EntryCell' は、
    'Microsoft.Maui.Controls.EntryCell' と 'KsSettingsView.EntryCell' 間のあいまいな参照です

  (両 TFM で同一の 2 件。TFM に依存しない C# の名前解決の問題である)

8-b. 完全修飾 / using alias で解消する場合

  using KsSettingsView;
  using KsvEntryCell = KsSettingsView.EntryCell;      // using alias
  ...
          _ = new global::KsSettingsView.SwitchCell();  // 完全修飾
          _ = new KsvEntryCell();

  $ dotnet build -c Debug -f net10.0-ios     -t:Compile   => ビルドに成功しました / 0 エラー
  $ dotnet build -c Debug -f net10.0-android -t:Compile   => ビルドに成功しました / 0 エラー

  => 衝突するのは SwitchCell と EntryCell の 2 型で、いずれも完全修飾または
     using alias で解消できる (deviation.md の合意どおり、型名・名前空間は変えない)。
     XAML では ks: prefix が名前空間を明示するため衝突しない
     (7-2 の SettingsPage.xaml が ks:SwitchCell を含んだままビルド成功している)。
