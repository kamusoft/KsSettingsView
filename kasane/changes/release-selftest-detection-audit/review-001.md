## 指摘事項

### [🟠 Major] 照会件数のリセットが検査で守られておらず、落とすと停止が戻る

**該当箇所**: `scripts/release/wait-for-registries.sh:344` (`poll_once` 冒頭の `POLL_PROBE_COUNT=0`)、検査は同 `:747-748`

**問題点**: 空回り巡回の打ち切り (`:414`) は「件数が巡回ごとに 0 から数え直される」ことに全面的に依存している。リセットの 1 行を落とすと件数は巡回をまたいで累積し、2 巡目以降は決して 0 にならないため歯止めが死ぬ。それでも自己テストは緑 (W3)。巡回上限判定と組み合わせると停止が復活する (W8 で 60 秒打ち切り、W1 単独なら 7 秒で NG)。つまり本 change が塞いだ穴が、今回書いた 1 行の消失で無検出のまま戻る。

守れていない理由は 2 つある。(1) `wait_for_registries` を回す検査はすべてコマンド置換 (`output="$( ... )"`) の中で走るため、親シェルの `POLL_PROBE_COUNT` は更新されない。親で値を見る検査は `poll_once` を直接呼ぶ 2 か所だけ。(2) その 2 か所が「空回り (期待 0) → 照会あり (期待 4)」の順に並んでおり、空回りを見る時点の値が初期値 0 のままなので、リセットが無くても通る。これは本 change が直そうとしている「検査が通る理由が別の層にある」型そのもの。

**推奨修正**: 照会を送った巡回の**後**に空回りを 1 回置き、件数が 0 へ戻ることを見る検査を `:756` の直後に足す。下の形で実測したところ、無変異では緑、W3 では `空回りした巡回の照会件数は前の巡回を持ち越さない (4)` で NG になった。

```bash
    # 照会を送った巡回の後にもう一度空回りさせ、件数が巡回ごとに 0 から数え直されることを見る。
    reset_targets
    POLL_DEADLINE=$(( SECONDS - 1 ))
    poll_once 1.2.3
    check "$([ "${POLL_PROBE_COUNT}" = "0" ] && echo 0 || echo 1)" \
        "空回りした巡回の照会件数は前の巡回を持ち越さない" "${POLL_PROBE_COUNT}"
    POLL_DEADLINE=$(( SECONDS + 3600 ))
```

### [🟠 Major] 「上限を過ぎれば失敗する」が、今回の追加によって上限判定を検出しなくなった

**該当箇所**: `scripts/release/central-portal.sh:489` (検証待ち)、同 `:578` (公開待ち)

**問題点**: どちらの検査も台本を 2 行だけ置いて上限 0 秒で回す形になっている。上限判定 (`:250` / `:304`) を削除すると、台本が尽きた 3 件目の照会が空文字を返し、**今回追加した空文字ガード (`:239` / `:289`) が代わりに失敗させる**。結果として C1 / C2 のどちらでも「上限を過ぎれば失敗する」は OK のまま通り、NG になるのは末尾の「台本を使い切った検査は無い」1 件だけになる。これは exploration が「後退」として記録した型 (終端を名乗る検査が別の理由で通る) と同じ形で、変更前は停止していた箇所が、今回の追加によって「名前と違う理由で緑になる検査」へ移った。決定事項 2 の手当 (照会回数の表明) が終端の検査だけに入り、上限の検査には入っていないことが原因。

**推奨修正**: 決定事項 2 と同じ手当を上限の 2 検査にも添える。下の 2 件を `:489` と `:578` の直後に足して実測したところ、無変異では緑、C1 / C2 ではそれぞれ名前の通りの検査が NG になった。

```bash
    check "$([ "$(calls | wc -l | tr -d ' ')" = "1" ] && echo 0 || echo 1)" \
        "上限を過ぎた検証待ちは 1 回目の照会で終わる" "$(calls)"
```

```bash
    check "$([ "$(calls | wc -l | tr -d ' ')" = "1" ] && echo 0 || echo 1)" \
        "上限を過ぎた公開待ちは 1 回目の照会で終わる" "$(calls)"
```

### [🟡 Minor] 公開待ちが一時的な不調を吸収しなくなったことが、どこにも書かれていない

**該当箇所**: `scripts/release/central-portal.sh:289` (`cmd_wait_published` の空文字ガード)

**問題点**: 決定事項 1 のとおりの実装であり違反ではないが、**本番の挙動が 1 つ変わっている**。`deployment_state` は 200 / 404 以外の応答で失敗するため、公開待ちの巡回中に Portal が 1 度でも 5xx / 429 を返すと空文字が届き、これまで上限まで回り続けて吸収していたものが即座に失敗になる。公開待ちは既定 90 分・30 秒間隔 (最大 180 回の照会) で、しかも `release` を送った後 — 取り消せない操作の後 — の位置にある。

検証待ち側 (`:239`) はこの変更で実質的な差が無い (空文字はこれまでも `*)` で「決着」として返され、`release.yml` の `*)` アームが `想定しない deployment の状態` で落としていた)。差が出るのは公開待ちだけである。

再実行での復帰は可能で (PUBLISHING の deployment は drop されず ID が引き継がれる)、`handbook/cross/release-procedure.md` の「publish の途中での失敗」の表と矛盾はしない。ただし同じリポジトリの `scripts/release/wait-for-registries.sh:28-31` は「判定不能でも待機は続ける。レジストリ側の一時的な不調で待ちを打ち切ると、公開そのものは済んでいるのに後段が走らない」と**逆の方針を明示している**。同じリリース経路で方針が分かれる理由が、コードにも手順書にも残っていない。

**推奨修正**: 次のいずれか。(a) 現状のまま、`cmd_wait_published` のコメントへ「一時的な不調でも即座に失敗する (再実行で同じ deployment の公開待ちから続く)」という選択の明示を 1 行足す。(b) 連続して空文字が返った回数で失敗させ、単発の不調は吸収する (検出力は維持できる — 台本が尽きた自己テストでは空文字が連続するため)。(a) で足りると考えるが、公開後の不可逆な位置なのでオーナー裁定を仰ぎたい。

### [🔵 Suggestion] `wait-for-registries.sh` の安全網が現時点では効いていない

**該当箇所**: `scripts/release/wait-for-registries.sh:457`

**問題点**: 決定事項 3 の実装だが、`wait_for_registries` を回す検査 4 か所はすべて `KSR_POLL_TIMEOUT_SECONDS` を明示的に渡しており、この export が効く呼び出しは 1 つも無い (削除しても緑 = W5)。コメントは「上限そのものを見る検査は、これを各呼び出しで明示的に上書きする」と書いているが、実際には上限を見ない検査も全部上書きしている。将来足す検査のための予防として残すのは妥当なので、コメントをその意図に合わせると誤読が減る。

**推奨修正**: コメントを「上限を渡さない検査が足されたときに、既定 (45 分) で呼び出し側のタイムアウトへ化けるのを防ぐ」旨へ言い換える。

### [🔵 Suggestion] 冒頭の subcommand 説明に新しい失敗条件が反映されていない

**該当箇所**: `scripts/release/central-portal.sh:22-30`

**問題点**: ファイル冒頭は `wait-validated` / `wait-published` の契約を「その状態を返す」「FAILED や NOT_FOUND は失敗ではなく状態として返す」と列挙しているが、今回加わった「状態を取り出せなければ失敗する」がここに無い。このファイルだけを読む人にとって、失敗条件の一覧が実装より狭く見える。

**推奨修正**: `wait-validated` / `wait-published` の行に、状態を取り出せなかった照会は失敗として扱う旨を 1 行添える。
