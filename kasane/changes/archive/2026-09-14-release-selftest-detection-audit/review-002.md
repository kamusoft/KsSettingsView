## 指摘事項

### [🔴 Critical] 公開待ちの吸収は本番の呼び出し文脈では動かない (裁定 (b) が未実現)

**該当箇所**: `scripts/release/central-portal.sh:293` (`cmd_wait_published` の `state="$(deployment_state "${id}")"`)、同 `:242` (`cmd_wait_validated`)、根拠となっているコメント `:199-202` / `:243-249` / `:294-300`、冒頭の契約 `:31-32`

**問題点**: 実装もコメントも deviation も「`deployment_state` の `fail` はコマンド置換のサブシェルしか終わらせないため、ここへは空文字が届く」という前提に立っている。この前提が成り立つのは **errexit が抑止された文脈だけ**で、自己テストの `if ( ... cmd_wait_published ... )` がまさにそれにあたる。本番は `main` の `case` から素のコマンドとして呼ばれ、スクリプト冒頭 (`:63`) の `set -euo pipefail` が効いているため、`state=$(...)` の代入はコマンド置換の終了コード 1 をそのまま引き継ぎ、**その場でスクリプトが終了する**。連続カウントにも空文字ガードにも到達しない。

本番と同じ文脈 (素のコマンドとして呼ぶ) を作って実測した。台本は 1 件目 503、2 件目 PUBLISHED:

| 実装 | 結果 |
|---|---|
| 現状 | exit 1 / 照会 1 件 / 出力は `::error::deployment の状態を照会できない (HTTP 503): abc` のみ |
| 下記の修正案 | exit 0 / 照会 2 件 / `待機中 (状態不明)` → `公開された` |

影響は 3 つある。

1. **オーナー裁定 (b) が届いていない**。release を送った後の待機は、Portal が 1 度 5xx / 429 を返した時点で従来どおり落ちる。裁定前の挙動と同じで、deviation に書かれた「単発の 5xx / 429 で待機を捨てない」は成立していない
2. **冒頭の契約 (`:31-32`) が実装と食い違う**。「単発なら吸収して待ち続け」はこのファイルだけを読む人への誤った説明になっている
3. **自己テストが本番に存在しない理由で緑になっている**。`状態を 1 度取り出せなくても公開待ちは続く` / `吸収した後は次の照会で決着する` / `状態を取り出せない公開待ちは許す回数で終わる` はいずれも errexit が抑止された文脈でしか成立しない。本 change が繰り返し潰してきた型 (終端検査 → 上限検査) の、いちばん根に近い実例

なお `cmd_wait_validated` 側は、到達しないまま `deployment_state` の失敗で落ちるため**結果は変わらない** (exit 1 と `::error::` 行)。壊れているのは公開待ちの吸収だけで、ガード自体は本番では死んだコードになっている。

**推奨修正**: 代入を errexit から切り離し、空文字を実際に届かせる。両待機関数の代入を次の形にすると、本番文脈で吸収が成立し (上表)、自己テストも緑のまま (OK 64 件 / NG 0 件) であることを実測した。

```bash
        state="$(deployment_state "${id}")" || state=""
```

より根から断つなら、`deployment_state` が照会できなかったことを `DEPLOYMENT_NOT_FOUND` と同じ**状態値**として返し (`fail` をやめる)、呼び出し側がそれで分岐する形もある。既に 404 で同じ設計を採っているので語彙は揃う。`cmd_status` / `cmd_release` / `cmd_drop` の扱いを決める必要があるぶん範囲は広い。どちらを採るかは実装側で判断してよいが、**採った後に本番と同じ文脈 (素のコマンドとして呼ぶ) で吸収を確かめること**。

あわせて、この型が戻らないようにする手当が要る。現状の検査はすべて errexit が抑止された文脈で走るので、上記の `|| state=""` を消しても自己テストは緑のままになる (検出力 0)。`( set -e; ... )` で張り直す方法は、手元の bash 3.2 では errexit が再武装されず効かないことを実測した (CI の bash 5 とで挙動が割れうる) ため、検査の文脈を変えるより、**errexit に依存しない実装 (上の 2 案どちらでも代入の成否に依らない形) にしたうえで、その旨をコメントで明示する**のが確実だと考える。

### [🟡 Minor] 吸収した照会が `::error::` 注釈を残したまま job は成功する

**該当箇所**: `scripts/release/central-portal.sh:206-224` (`deployment_state` の `fail`)、`:293-308` (吸収する側)

**問題点**: 指摘 1 を直すと、吸収された照会でも `deployment_state` の `fail` が先に `::error::deployment の状態を照会できない (HTTP 503): abc` を出す (修正案での実測で確認)。GitHub Actions ではこれが run の注釈として赤く残るため、**成功した publish に error 注釈が並ぶ**ことになる。手順書の「4. 見守り」は run を見て進行を判断する段なので、吸収したのか落ちたのかが注釈からは読み分けられない。

**推奨修正**: 吸収した側で「何回目まで許したか」を 1 行出す (例: `状態を取り出せなかった (1/3): 待機を続ける`)。`待機中 (状態不明)` だけでは、直前の `::error::` が致命なのか吸収済みなのかが分からない。`deployment_state` 側の `::error::` を出し分ける手もあるが、`cmd_status` / `cmd_release` からの呼び出しでは致命なので、呼び出し側で補う方が影響が小さい。

### [🔵 Suggestion] 許す回数の上側は「台本を使い切った検査」でしか止まっていない

**該当箇所**: `scripts/release/central-portal.sh:594-595`

**問題点**: `状態を取り出せない公開待ちは許す回数で終わる` は照会回数を `${PUBLISHED_UNRESOLVED_STATE_LIMIT}` と突き合わせる形なので、定数を増やす変異 (3 → 4 / 10 / 180) では常に通り、NG になるのは末尾の「台本を使い切った検査は無い」だけになる (D7 / D8 / D9)。定数の値そのものは自己テストでは判定できない (リテラルを二重に持つことになる) ので**現状の形で妥当**と考えるが、境界の意味 — 許す回数ちょうどで終わり、その 1 つ手前は吸収する — のうち後半が `1 回` でしか確かめられていない。回数を 3 から動かす議論が起きたときは、`許す回数 - 1` 回の連続を吸収する検査を足すと境界が両側から留まる。

## 閾値 3 の評価 (依頼 3 への回答)

結論: **妥当**。修正すべき点は見つからなかった。

| 観点 | 値 |
|---|---|
| 許容する連続失敗 | 2 回 (3 回目で失敗) |
| 最短で諦めるまで | 約 60 秒 (即答の 5xx が 3 回 + 間隔 30 秒 x 2) |
| 最長で諦めるまで | 約 16.5 分 (応答上限 300 秒 x 3 + 間隔 30 秒 x 2) |
| 公開待ちの上限 | 5400 秒 = 90 分 (巡回は最大 180 回) |
| 時間予算への影響 | なし。連続カウントは期限より**早く**終わらせる方向にしか効かず、`check-time-budget.py` は緑のまま (publish 余裕 23 分) |

- **短すぎないか**: 90 分の待機のうち 2 回の連続失敗まで許す。Portal の単発の 5xx / 429 (裁定が挙げた事例) は 1 回で吸収され、90 秒を超える連続停止だけが待機を終わらせる。release 直後の deployment は PUBLISHING で drop されないため ID は引き継がれ、`handbook/cross/release-procedure.md` の「publish の途中での失敗」の表どおり失敗した job からの再実行で公開待ちから続けられる。取り返しのつかない状態にはならない
- **長すぎないか**: 最長 16.5 分の遅延は 90 分の予算内で、job の `timeout-minutes: 240` にも余裕がある。吸収中も期限判定は毎巡回効くので、上限を越えて居座ることはない
- **失敗の文面**: 「3 回続けて取り出せなかった」は回数だけで、上の表のとおり実時間は 60 秒〜16.5 分と幅がある。`wait-for-registries.sh` が「遅いのか壊れているのか」を出力から読み分けられるようにしている流儀に合わせるなら、経過を添えてもよい (指摘 2 と同じ箇所なのでまとめて直せる)
