# Exploration: release-selftest-detection-audit

## 課題 / 動機

KsDialogs からの知らせ (`../KsDialogs/kasane/outbox/KsSettingsView/2026-09-13-backport-result-and-time-budget-divergence.md`)
で、リリーススクリプトの自己テストに「待機の止まらない誤実装を、失敗ではなく停止として表す」穴があったと
報告された。相手はこれを塞ぐのに 3 サイクルを要し、最終形は三層になった — 内側 (答えの返らない照会を待機
対象に残さず失敗させる)、外側 (公開待ちを回す検査に短い上限を与える)、そして上限に達した理由を区別する
ための照会回数の表明。検証は誤実装のスイープで行い、`central-portal.sh` に 18 種・`wait-for-registries.sh`
に 7 種の単一誤実装を注入して、停止 0 件・19 種が NG になることを確認したという。

こちらの `scripts/release/central-portal.sh` は、相手の言う三点に相当するものを既に持って**見える**:

- 外側の安全網 — selftest 冒頭で `KSR_POLL_TIMEOUT_SECONDS=5` / `KSR_PUBLISHED_TIMEOUT_SECONDS=5` を
  export する (scripts/release/central-portal.sh:365)
- 終端状態の検査 — 「FAILED になれば失敗する」「存在しない deployment の公開待ちは失敗する」(同 :516, :531)
- 照会回数の表明 — 「PUBLISHED まで照会を繰り返す」で呼び出し回数を 3 と突き合わせる (同 :528)
- 台本尽きの検出 — モックの台本が尽きたことを印として残し、最後にまとめて見る (同 :358)

揃って**見える**ことと、誤実装を入れて実際に NG が**出る**ことは別である。相手が踏んだ後退 — 上限判定を
丸ごと外しても自己テストが緑になる — は、まさに安全網が効いているときにこそ起こる型で、こちらの同じ箇所の
コメントも「この自己テストで効いているのは、冒頭で安全網として置いた 5 秒であって既定値ではない」と
自覚した書き方をしている (同 :539)。検出力そのものは未検証のまま残っている。

## 検証: 誤実装スイープの結果 (2026-09-13)

単一の誤実装を 1 箇所ずつ注入した写しで `--selftest` を回し、17 種を測った (写しはスクラッチパッド。
リポジトリの `scripts/` は無改変)。**緑 (見逃し) は 0 件**、穴は次の 3 型。

| 型 | 注入 | 結果 | 原因 |
|---|---|---|---|
| 停止 1 | `cmd_wait_published` の上限判定を削除 | 停止 (30 秒で 2313 周) | `case` に catch-all が無く、空文字の状態がどのアームにも当たらず回り続ける |
| 停止 2 | `wait_for_registries` の巡回上限判定を削除 | 停止 (40 秒で 8 周) | この本の自己テストには冒頭の安全網が無く、上限を外すと外側の受け皿が残らない |
| 後退 | `FAILED` / `NOT_FOUND` のアームを削除 | NG だが「台本を使い切った検査は無い」1 件だけ | 終端の検査が、終端の検出ではなく安全網の 5 秒で上限に達して通っている (その表明も外した二重変異で緑になることを確認) |

後退の型は、KsDialogs が踏んだ「上限判定を外しても緑になる」の裏返し — 終端を名乗る検査が上限で通っている。

### 停止の機構 (2 段)

- ループを終わらせる唯一の出口が上限判定だけになる。台本が尽きたモックは `return 1` を返すが、検査は
  `if ( ... )` 条件下で走るため `set -e` が抑止され、`deployment_state` 内の `fail` はコマンド置換の
  サブシェルしか終わらせない。呼び出し側には**空文字の状態**が届き、ループは回り続ける
- 台本尽きの印 (`MOCK_EXHAUSTED`) は書かれているが、それを見る表明がループの**下流**にある
  (central-portal.sh:585)。ループが返らない以上そこへ到達しない。「対」の層はあるが停止には構造上効かない

### 2 本の設計の非対称

- `cmd_wait_validated` (:233) — 継続する状態を列挙し (`PENDING|VALIDATING`)、`*)` で決着として返す。
  空文字も `*)` に落ちるのでループは返る (ただし空文字を「決着した状態」として表明してしまう)
- `cmd_wait_published` (:275) — 決着する状態を 3 つ列挙し、それ以外はすべて継続。空文字が継続に落ちる

同じ誤実装が、catch-all の有無だけで NG と停止に分かれている。

### `wait-for-registries.sh` の方針は逆

こちらはリスト形だが、状態を取り出せなかった対象は失敗にせず「判定不能」として**意図的に待機対象へ残す**
(:29-31)。レジストリ側の一時的な不調で公開済みの待ちを打ち切らないための設計判断であり、停止を止める責任が
全面的に上限判定側に寄っている。W10a が停止になったのはその必然。

## 検討した選択肢 (却下案と理由を含む)

停止 1 の塞ぎ方:

- **採用候補: 空文字 (状態を取り出せなかった) だけを失敗にする** — KsDialogs の「内側の層」に対応する。
  未知の状態名には現状どおり上限まで耐えるので、Portal 側が状態名を足しても即死しない
- 却下: 継続する状態を列挙して未知はすべて失敗 (`cmd_wait_validated` と同じ allowlist 型に揃える) —
  対称にはなるが、Maven Central Portal が状態名を足した時点でリリースが即失敗する
- 却下: 自己テストの安全網だけで済ませる — 上限判定を守る検査が無いままになり、停止 1 がそのまま残る

## 決定事項

- 変更級は **S 級** (2026-09-13 確定)。提案アーティファクトは作らず直接実装へ進み、独立レビューで締める
- 停止 1 は「空文字 (状態を取り出せなかった) を失敗として受け止める」で塞ぐ。`cmd_wait_validated` と同じ
  allowlist 型 (継続状態を列挙し未知はすべて失敗) には**しない** — Maven Central Portal が状態名を足した
  時点でリリースが即失敗するため
- `cmd_wait_validated` が空文字を「決着した状態」として返す件は、同じ修正で併せて解消する (別 change に
  逃がさない)

## 変更級: S (確定)

判定材料 — 触るのは release の待機機構という単一能力内の 2 ファイル、公開 API の変更なし、可逆で局所的、
UI なし。KsDialogs は M 級だったが、相手の M 級には 4 状態分類の導入・時間予算の機械検査・自己テストの
lint job 接続が含まれ、こちらはそれらを既に持っている。残るのは検出力の 3 型だけ。

塞ぐ範囲:

1. 両待機関数で、状態を取り出せなかった (空文字) 場合を失敗として受け止める
2. `cmd_wait_published` の終端検査に照会回数の表明を添え、安全網ではなく終端の検出で通ることを担保する
3. `wait-for-registries.sh` の自己テスト冒頭に安全網を足す (central-portal.sh:367 と同じ形)
4. 塞いだ後に誤実装スイープを再実行し、停止 0 件・緑 0 件を確認する
