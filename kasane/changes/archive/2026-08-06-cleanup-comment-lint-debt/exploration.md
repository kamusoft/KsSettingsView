## 検討した選択肢 (却下案と理由を含む)

### 論点1: スコープの分割単位

- **採用: A — 1 change 一括、tasks を領域単位に切って段階コミット**
  - 書き換え判断の基準が全領域で共通であり、change を分けると同じ判断を毎回議論し直すことになる
  - 衝突の窓が空いている今なら分割して長期化させる利点が薄い
- 却下 B (領域単位で 4〜5 change): diff は最小になるが、change ごとに判断基準を再議論することになり、完了まで L-001 の債務が残り続ける
- 却下 C (類型単位で分割): 同じコメントブロックに複数類型が混在する (`// 設計: openspec/... Decision 2` はパス参照+通番) ため、同じ行を複数回触る自己衝突が起きる

### 論点2: 理由一体型の書き換えで ADR 対応付けをどこまで探すか

規約 (`concepts/cross/conventions/comment-policy.md` 類型2) は「対応 ADR があれば `<domain>/ADR-NNNN` に置換、無ければ自己完結説明、新規 ADR は起票しない」と定めている。決まっていなかったのは **対応 ADR を探す努力量**。

- **採用: α — 自己完結説明への書き直しを既定とする**
  - ADR 参照に置換するのは、コメントの説明だけでは理由が語れず、かつ **ADR の index.md 上のタイトルレベルで明らかに一致する**場合のみ (ADR 全文の読み込みはしない)
  - それ以外は現在形の自己完結説明に書き直す
  - 「設計（履歴）: openspec/.../archive/...」のような履歴参照は類型3として削除。失われる情報が惜しい場合だけ現在形の仕様説明に翻案する
  - 判断に迷った箇所は勝手に決めず、実装後の報告にリストとして上げてオーナー確認に回す
- 却下 β (全 320 件を 40 ADR と突合): 工数が突合コストに支配されるうえ、「たぶんこの ADR だろう」という誤参照を作り込むリスクがコメントの信頼性を損なう
- 却下 γ (参照を全部落として説明も足さない): ADR 置換を第一選択とする規約と不整合。理由が消える箇所が出る

### 論点3: 再発防止 (CI ゲート化) を含めるか

現状、このリポジトリに CI は存在しない (`.github` 自体が無い)。再発防止は書き込み前 hook のみで、これはエージェント経由の Write/Edit だけを守る。

- **採用: A — 含めない。債務返済に純化する**
  - CI ワークフロー新設は「Swift Package / Gradle / MAUI のマルチプラットフォームビルドをどこでどう回すか」という別テーマの判断を連れてくる
  - 765 件を 0 にすること自体が最大の再発防止になる。0 になれば hook が本来の仕事 (新規混入を1件目で止める) を果たす
- 却下 B (CI ゲートも新設): change の性格が変わり、級も一段上がる
- 却下 C (lint 整備だけ足す): 既に `--summary` があり追加価値が薄い

### 論点4: 変更級

この change は S/M/L の軸 (機能変更の影響範囲) に素直に乗らない。「複数能力横断」は文字通り該当する一方、公開 API も挙動も変わらず revert で完全に戻せる。

- **採用: A — S 級 + tasks.md のみ作成**
  - M/L が要求するデルタスペックが実質書けない (挙動が変わらないため Scenario が「lint の禁止件数が 0」の1本に収束する)
  - 一方 215 ファイル・領域5分割の作業は進捗管理なしには回らないため tasks.md は必要
  - 「迷ったら1段上」に反するが、上げた先で増えるアーティファクトが空虚になるケース。儀式の重さではなくレビューの厳しさで担保する (S 級でも独立レビューは必須)
- 却下 B (M 級): proposal + デルタスペックが空虚になる
- 却下 C (S のまま何も作らない): 215 ファイルの進捗管理ができず迷子になる

## 決定事項

1. 1 change 一括で全 765 件を返済する。tasks.md を領域単位 (ios/Sources、ios/Tests、android/ks-settingsview-ui、android/ks-settingsview-core、android/ks-settingsview-compose、samples) に切り、段階コミットする
2. 書き換えは規約の3類型に従う。ADR 参照への置換は index.md のタイトルで明らかに一致する場合のみ。それ以外は現在形の自己完結説明。新規 ADR は起票しない。迷った箇所はオーナー確認に回す
3. CI ゲート新設はスコープ外 (別 change として起票する)
4. 変更級は S。アーティファクトは tasks.md のみ (proposal / デルタスペックは作らない)。独立レビューは実施する
5. 機能コードは1文字も変えない。差分はコメント行のみ

## tasks.md の完了条件 (実装フェーズへの申し送り)

- 領域ごとに `python3 scripts/comment-policy-lint.py <領域>` の禁止件数 0
- 全体で `python3 scripts/comment-policy-lint.py --summary` の禁止件数 0
- 機能コードの差分が 0 であること (diff がコメント行のみであることの確認)
- 各プラットフォームのビルド・テストが通ること (doc comment 破壊の検出)
- α で判断に迷った箇所のリスト (オーナー確認用)
