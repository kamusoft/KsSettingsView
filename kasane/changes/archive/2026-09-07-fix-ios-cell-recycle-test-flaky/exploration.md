# Exploration: fix-ios-cell-recycle-test-flaky

## 課題 / 動機

iOS の Bridge テスト `KsBridgeCustomCellTests` の「リサイクルを挟んだ再表示で内容が壊れない」(`ios/Tests/KsSettingsViewBridgeTests/KsBridgeCustomCellTests.swift`) が、GitHub Actions の macOS ランナー上で条件待機の deadline 超過により失敗する。

発見の文脈: 0.1.0-beta.2 のリリース作業で develop へ push した検証 CI (run 34035445799、job `ios / verify`、2026-09-06) で、`ios / verify` だけがこのテスト 1 件で失敗した。同じ run の `android / verify` / `maui / verify` / `lint` は成功している。

| 回 | 待機の経過 / deadline | テストケース全体 | 結果 |
|---|---|---|---|
| attempt 1 | 3.042 秒 / 3.000 秒 | 6.326 秒 | 失敗 |
| attempt 2 | 5.599 秒 / 3.000 秒 | 30.985 秒 | 失敗 |

失敗時のセルはいずれも `hidden = YES`、`frame = (0 21.6667; 375 52)` で、可視矩形の外にある。それでも `collectionView.cellForItem(at:)` が nil を返さない。

## 検討した選択肢 (却下案と理由を含む)

- 待機の既定 deadline (`KsTestWait.defaultDeadline` = 3.0 秒) を引き上げる案: attempt 2 は 5.599 秒でも成立しておらず、待ち時間の不足だけが原因とは言えないため却下した。先例でも「時間の長さで誤失敗を減らすだけ」として却下されている。
- 再実行を重ねて通るのを待つ案: 2 回連続で同じテストが同じ理由で落ちており、超過幅も 3.042 → 5.599 秒と広がっているため、偶発とみなせず却下した。
- 回収の判定を行の位置で行う案: `cellForItem(at:)` が nil を返す時期は UIKit の保持方針と実行機の速さに依存する一方、行が可視矩形と交わるかは表示の意味そのもので環境に依らないため採用した。
- 内容の漏れの検査対象を可視矩形と交わる行に限る案: 画面外に残っている行は表示に寄与せず、そこに内容が付いたままでも利用者から見た欠陥にならないため採用した。
- `contentOffset` の代入を `scrollToItem` へ変える案: 回収の時期を UIKit に委ねる点は変わらず、判定の脆さは解消しないため採らなかった。

## 決定事項

- 画面外の判定に `cellForItem(at:) == nil` を使わず、行の frame が可視矩形と交わらないことで判定する
- 内容の漏れの検査は可視矩形と交わる行だけを対象にする
- 待機の deadline は既定の 3.0 秒のまま変えない
- 失敗時の観測値に、先頭行の frame / hidden、可視矩形、内容が取り付いたままの行を出し、次に落ちたときにどちらの条件で止まったかを切り分けられるようにする
- 変更対象はテスト 1 ファイルに限り、製品コードには触れない

## ADR 候補 (作成済み: なし / 未起票: なし)

## 未決の論点

- 同じ待機ヘルパを使う他のテストは CI で通っており、横断修正は行っていない。同型の脆さが他にもあるかは未確認

## 検証結果

修正後の CI (run 34036938109、job `ios / verify`) で iOS 1027 件 / 0 failures (Bridge 166 / Core 88 / SwiftUI 96 / TestSupport 7 / UI 670)。対象テストは 0.092 秒で成立した。

この結果は真因を確定させる。同じ run で Bridge バンドル全体は 34.646 秒かかっており (手元は 7.092 秒)、実行機の遅さは修正前と変わっていない。それでも位置による判定は即座に成立したので、行は待機の開始時点で既に可視矩形の外にあり、内容もどの表示中の行にも残っていなかった。待機が 3〜5.6 秒成立しなかったのは、`cellForItem(at:)` が可視矩形の外にある行を返し続けたことだけが理由で、回収の遅れでも内容の取り残しでもない。

## 蒸留時の方針

`kasane/handbook/cross/test-execution.md` の「収束を待つアサーション (platform 共通)」節への追記を検討する。同節は待ち方の作法 (実時間 deadline・実行機会の譲渡・超過時の実測値報告) を定めているが、**何を待機条件に選ぶか**は扱っていない。今回の失敗は作法をすべて満たした待機が、条件の選び方だけで CI 専用の誤失敗になった事例にあたる。

一般化すると「framework の内部的な保持タイミングに依存する値を遷移証拠に使わず、観測したい意味そのもの (ここでは行が可視矩形と交わるか) を条件にする」。`cellForItem(at:)` が可視矩形の外の行を返し続けるかは UIKit の裁量で、実行機が遅いほど長く残るため、手元では常に緑で CI でだけ落ちる — 同節が既に警告している症状と同じ形で表面化する。
