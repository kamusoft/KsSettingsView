# release-workflow デルタスペック

## MODIFIED Requirements

### Requirement: Maven Central の公開待ち

publish は、Maven Central への release 要求の後、当該 version が公開されたことを確認できるまで待つ SHALL。

- 公開を待つ上限は、検証の決着を待つ上限とは独立に設定できる SHALL。
- 公開を待つ上限の既定値は 90 分とする。
- publish の実行時間の上限は、次の各項の合計以上である SHALL。

  | 項 | 内訳 | 分 |
  |---|---|---|
  | 待機の上限 | 検証の決着待ち 30 × 2 + 公開待ち 90 | 150 |
  | 各待ちの最後の照会 | 照会 1 回あたりの応答上限 5 × 3 待ち | 15 |
  | 各待ちの巡回間隔の端数 | 巡回間隔 0.5 × 3 待ち | 2 |
  | 待機外の照会 | 引き継いだ deployment が検証に失敗する分岐での要求 6 回 × 5 | 30 |
  | 本体処理 | 成果物の取得・署名つき再ビルド・publish 操作 | 20 |
  | 余裕 | | 23 |
  | **合計** | | **240** |

  この条件を満たす値として 240 分とする。各項の定数 (待機の上限・応答上限・巡回間隔) を変えたときに、合計が実行時間の上限を超えていないことを機械的に検査できる SHALL。

#### Scenario: 同期に時間がかかっても公開を待ち切る
- **GIVEN** Maven Central の同期に 60 分を要する状態
- **WHEN** publish が release を要求して公開を待つ
- **THEN** 公開が確認され、publish は成功する

#### Scenario: 検証待ちと公開待ちの上限を別々に設定できる
- **GIVEN** 検証の決着待ちと公開待ちに異なる上限を設定した実行
- **WHEN** publish が両方の待ちを行う
- **THEN** それぞれの待ちが自分に設定された上限に従う

#### Scenario: 時間予算が待ちの最悪ケースと応答上限を収容する
- **GIVEN** 設定された各待ちの上限、照会 1 回あたりの応答上限、publish の実行時間上限
- **WHEN** 設定値を算出式に当てはめる
- **THEN** 待ちの最悪ケースと応答上限の超過分を足しても、publish の実行時間上限に達しない

### Requirement: 公開レジストリへの反映待ち

公開後の反映待ちは、照会できたうえで未反映であることと、照会そのものが行えなかったことを区別する SHALL。

- この区別は、待機の対象それぞれについて独立に保つ SHALL。対象は Maven Central の座標 1 件と nuget.org の Package ID 3 件である。
- 判定不能は、失敗の種別 (通信そのものの失敗 / 応答が成功を示さない / 応答を解釈できない) まで区別する SHALL。
- いずれの場合も待機を継続する SHALL。照会が行えなかったことを理由に即座に失敗しない。
- いったん反映済みと判定した対象は、以後の巡回で再照会せず反映済みのまま扱う SHALL。出力に示す分類は、その時点で各対象が保持している分類とする。
- 上限に達して失敗するときは、対象ごとに保持している分類を出力に含める SHALL。

#### Scenario: 未反映は待機を続ける
- **GIVEN** 当該 version がまだ反映されていない対象
- **WHEN** 反映待ちが照会する
- **THEN** 未反映として扱われ、待機が続く

#### Scenario: 照会できなかった場合も待機を続ける
- **GIVEN** 対象が一時的に応答しない、または応答を解釈できない状態
- **WHEN** 反映待ちが照会する
- **THEN** 判定不能として失敗の種別つきで記録され、未反映と区別できる形で待機が続く

#### Scenario: 判定不能から回復すれば反映済みになる
- **GIVEN** 前の巡回で判定不能だった対象
- **WHEN** 次の巡回で照会が成功し、当該 version が反映されている
- **THEN** その対象は反映済みとして扱われ、以後は再照会されない

#### Scenario: 対象ごとに状態が分かれて残る
- **GIVEN** 一部の対象が反映済み、一部が未反映、一部が判定不能である状態
- **WHEN** 反映待ちが 1 巡する
- **THEN** 4 つの対象それぞれについて、その時点で保持している分類が分かる

#### Scenario: 上限超過時に対象ごとの最後の状態が分かる
- **GIVEN** 上限まで反映が確認できなかった実行
- **WHEN** 反映待ちが失敗する
- **THEN** 失敗の出力に、対象ごとに保持している分類と、判定不能であればその種別が含まれる

### Requirement: 保留中 deployment の引き継ぎ

同じ version の再実行は、前の試行が残した保留中の Maven deployment を引き継ぎ、その決着から続ける SHALL。

- 引き継ぎの読み込みは、publish が必要とする他の成果物の取得よりも先に行う SHALL。
- 引き継ぎを読み込んだかどうかと、引き継ぎが存在したかどうかは、実行の出力から区別できる SHALL。

#### Scenario: 引き継ぎの読み込みが他の成果物の取得より先に行われる
- **GIVEN** 保留中の deployment を残した前の試行がある再実行
- **WHEN** publish が成果物の取得に失敗する
- **THEN** その時点で引き継ぎの読み込みは既に完了しており、読み込んだ結果が出力に残っている

#### Scenario: 引き継ぎが無い初回の実行と区別できる
- **GIVEN** 前の試行が存在しない初回の実行
- **WHEN** publish が引き継ぎを読み込む
- **THEN** 引き継ぎが存在しなかったことが出力に残り、読み込みに失敗した場合と区別できる

## ADDED Requirements

### Requirement: 待機スクリプトの自己テスト

リリースで使う待機スクリプトは、ネットワークに出ずに判定ロジックを検査する自己テストを持ち、その自己テストが日常の検証 CI で実行される SHALL。

publish の待機経路は不可逆な公開の後にしか到達しないため、判定ロジックの誤りをリリース時に初めて知ることがないようにする。

#### Scenario: 待機スクリプトの自己テストが lint job で走る
- **GIVEN** 待機スクリプトを変更した状態
- **WHEN** 検証 CI の lint job が実行される
- **THEN** 待機スクリプトの自己テストが実行され、失敗すれば lint job が落ちる
