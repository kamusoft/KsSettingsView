# Deviation: investigate-maui-icon-lease-sharing

- 共有防御の機構全体 (Requirement: 共有 platform 画像の後片付け安全性): spec では「参照カウントで後片付けを遅延し、最後のリースの破棄で保持していた後片付け口を実行する」前提 (proposal What Changes 2 の参照カウント機構、Scenario「最後のリースの破棄で後片付けが実行される」) → オーナー指示により「解決時の所有権分類」へ設計変更。理由: `UIImage.FromBundle` が返す画像は UIKit のシステムキャッシュが所有し、managed 側の `Dispose()` は native メモリを解放せず (キャッシュが retain を保持)、共有 managed peer を無効化して他リースの表示を壊す効果しかない — 破棄自体が所有権の誤認。iOS resolver で cache 所有 (MAUI `FileImageSourceService` の FromBundle フォールバック分岐 = `File.Exists` false) を分類し、cache 所有画像には後片付け口を付けない (破棄 no-op、寿命は UIKit が管理)。private な画像 (CGImageSource / URI / stream / font 経路) は従来どおりリース破棄時に即時後片付け。これに伴い `KsSharedImageRegistry` (プロセス全域 static の参照カウント表) は廃止 — 相方レビュー (second-opinion-code-001 指摘 4) が突いた「リース放棄時に static 表が画像を恒久強参照する」退行も構造ごと解消される。spec への読み替え: Requirement 本文の SHALL NOT (他リースの表示を壊さない)・「リースが残っている間 後片付け 0 回」・「非共有画像は直ちに後片付け」・StoreIcon 同一画像の即時解放は引き続き成立。「最後のリースの破棄で全後片付け口を各 1 回実行しエントリ除去」のみ cache 所有画像には適用しない (そもそも保持しない) と読み替える。分類の自己検証: `File.Exists` false 分岐では `UIImage.FromBundle` 再呼び出しの `ReferenceEquals` で共有を実測確認できる (この分岐ではキャッシュ済みのため副作用なし)。誤分類時の失敗モードは「破棄しない」側 (GC 回収可能な一時リーク) に倒し、表示破壊側には決して倒さない (2026-08-25)。**注: 本項に書いた判定方法 (`File.Exists` 分岐ミラー) はレビューを受けて撤回済み — 判定の正は下の [設計判断] 項 (実体同一性のみで判定)。蒸留時は本項の狙い (所有権分類・破棄しない側へ倒す) と [設計判断] 項の機構を読むこと**
- 上記に伴い、下の「代表 1 件保持」の項は registry 廃止により役目を終えた (経緯記録として残す) (2026-08-25)
- [設計判断] 所有権分類の判定方法 (上記項の続き): deviation 起草時は「MAUI `FileImageSourceService` の分岐をミラー (`File.Exists` true → private)」を想定していた → レビューサイクル 3 (review-003 Major 1・2、相方も同一の核心指摘) を受けて **分岐のミラーをやめ、キャッシュへの引き直しと `ReferenceEquals` による実体同一性の確認だけで判定する**形に変更。(i) 照合キーは MAUI と同じ「ディレクトリと拡張子を落とした名前」(`Path.GetFileNameWithoutExtension`) に揃える — Microsoft.Maui.Core 10.0.70 の `ImageSourceExtensions.GetPlatformImage(IFileImageSource)` は `UIImage.FromBundle(Path.GetFileNameWithoutExtension(file)) ?? UIImage.FromFile(file)` であり、生の指定で引くと asset catalog 画像を拡張子付きで指定したときに照合が空振りして表示破壊側へ誤分類する (Simulator で実測再現・`evidence/ios-wiring-before-after.txt`)。(ii) `File.Exists` による短絡は**撤去**した (レビュー提示の選択肢 (b) を採用)。短絡は「破棄する側」を無検証で確定するため、MAUI の分岐と食い違った瞬間に「誤分類は破棄しない側にだけ倒す」という本設計の安全側不変条件が崩れる。分岐を推し量る実装は、推し量る先 (MAUI の内部分岐) が変わると黙って壊れる — Major 1・2 はまさにそれで生まれた。撤去の代償は「ファイルから起こした画像でも、同名の資産があると引き直しが名前付き画像キャッシュへの常駐を 1 件増やし得る」こと (UIKit 管理でメモリ逼迫時に purge される) で、表示破壊の可能性と引き換えに受け入れる。なお「実ファイルはあるが復号不能」ケースを以前「解決失敗で実害なし」と評価したのは誤り (review-003 が 10.0.70 の実装で反証。復号失敗は例外にならずキャッシュ引きへフォールバックする) — 短絡撤去によりこのケースも実体同一性で正しく分類される (2026-08-25)
- [読み替え] tasks 2.1 / 3.2 は「参照カウント機構」とその不変条件 (underflow・カウント 0 での全後片付け実行) を要求する文言のままチェック済みだが、上記の設計変更により**所有権分類 (`KsFileImageOwnership`) と `FileImageOwnershipTests` で満たしたもの**として読む。蒸留時は tasks の文言ではなくこの記録を正とすること (2026-08-25)

- 共有表の後片付け口の保持 (proposal「What Changes」2): proposal では「各解決結果の後片付け口は共有表が保持し、カウント 0 で全てを各1回実行する」→ レビューサイクル 2 (review-001 Major: Host 再接続ごとに口が無限成長、実測 50 回で 51 個保持) により「代表 1 件だけ保持し、後着の口は実行せずに落とす」へ変更。理由: iOS の全後片付け口は同一 UIImage への `Dispose()` のみで等価 (`ImageSourceServiceResult` は `Value` と `Action? _dispose` 以外の固有資源を持たない — dotnet/maui 実ソースで裏取り)。デルタスペック文言「保持されていた全ての後片付け口が各 1 回だけ実行され」は保持集合の大きさを規定しないため spec 違反なし (review-002 で許容判定・verify-002 VALID)。前提「同一画像への後片付けは互いに等価」を満たさない platform の結果をこの表へ通してはいけない制約は `KsSharedImageRegistry` の doc コメントに明記済み。蒸留時は proposal の当該記述ではなくこの記録を正とすること (2026-08-25)
- [付随修正] `DisposeRetiredViews` の例外安全 (review-002 Minor): icon 側 `DisposeRetired` と同型の「1 件の破棄失敗で後続の実体が取りこぼされる」無保護ループが View リース側にも残っていたため、同じ収集パターン (全件試行 + `AggregateException` 集約) へ揃えた。本 change が触れたファイル内・数行の修正 (lessons process L-005) (2026-08-25)
