# Deviation: add-scroll-control

- design Decision 5 (iOS の送り方): design では「行は `scrollToItem`、見出しと両端はレイアウト属性から求めた位置へ `setContentOffset`」→ 実装では行も見出し・両端と同じくレイアウト属性から求めた位置へ `setContentOffset` で送る。理由: 端での停止・表示範囲より高い行の start 合わせ・到着後の同じ向きの補正を 1 つの計算にまとめるため。spec の位置の定義 (Cell への命令の位置) は変わらない (2026-09-29)
- Requirement: Host への接続と最後の接続 (spec は未実行の命令の扱いを定めていない): 実装判断として、Host の `scrollController` を差し替えた・`nil` にしたときは、その Host に積まれた未実行の命令を捨てる。控えた位置の復元 (`restoreScrollAnchor`) は Host 自身への要求なので捨てない。Android も同じ扱いにそろえる。理由: 「接続を外したハンドルの命令は何も起こさない」と同じ向きにそろえるため (2026-09-29)
- design Decision 5 (Android の送り方): design では「アニメーションありは Start / Center / End の合わせを持つ `LinearSmoothScroller`」→ 実装では、行き先に要る行が配置済みで最終位置がその場で求まるときは `RecyclerView.smoothScrollBy` で一度に送り、配置されていないときだけ `LinearSmoothScroller` の派生で対象へ向かいながら、必要な行が配置されるたびに最終位置を解き直して減速して止める (snap の合わせは使わない)。理由: Section の範囲 (複数行) の中央・下端合わせと「表示範囲より高い範囲は上端」を、1 行の snap では表せないため。一方向の着地と位置の定義は変わらない (2026-09-30)
- Requirement: スクロール命令ハンドルの公開 / Host への接続と最後の接続 (Android の「debug ビルド」): Android ライブラリは BuildConfig を持たないため、spec の「debug ビルドで例外 / 警告ログ」を既存の debug 相当の切り替え `KsCellRegistry.strictMode` (既定 true、利用者が `BuildConfig.DEBUG` を代入する前提) で判定する。既定のままのリリースビルドでもメインスレッド以外からの命令は例外になる。理由: 未登録 Cell の検出など既存の debug 相当の挙動とそろえるため (2026-09-30)
- Requirement: スクロール命令ハンドルの公開 (spec は strictMode = false 時のメインスレッド以外からの命令を定めていない): 実装判断として、捨てずにメインスレッドへ post して実行する。メインスレッドかどうかの判定は接続中のときだけ行う (KsCollectionView と同じ) (2026-09-30)
- Requirement: Activity の作り直しで位置を戻す (spec は作り直し時の命令と復元の順を定めていない): 実装判断として、保存状態からの復元は待ち行列に積まれた順で実行する。`onCreate` の中で出した命令は復元より先に積まれるため、最終位置は復元した位置になる。`onCreate` より後に出した命令は復元の後に実行され、最終位置を決める (2026-09-30)
- Requirement: 準備完了のコマンド (spec は同じ Host の取り付けが繰り返し届いた場合と Host 生成の失敗時を定めていない): 実装判断として、合図は Host の世代ごとに 1 回だけ出す (view 階層から外れて戻るたびに届く Loaded では出し直さない)。Host の生成が途中で失敗した世代では出さない (2026-09-30)
- Requirement: 命令の対象の解決 (spec は `target` に null が渡された場合を定めていない): 実装判断として、null は解決できない対象として扱い、gateway を呼ばず Debug に警告を出す。解決は gateway へ配信済み (対応表に登録済み) の要素だけを対象にし、ItemsSource の生成物を利用者が生成先から手で外した場合はその生成物を飛ばして次の一致を探す (2026-09-30)
- Requirement: 命令の gateway 経路と Host が無い間の扱い: gateway 未接続時の命令も、解決できない対象と同じく Debug に英語の警告を出す (design Decision 10 の「見つからない・gateway 未接続なら no-op とし、Debug 出力に英語の警告」に従う) (2026-09-30)
- Requirement: SettingsView が作った命令ハンドルを ViewModel へ渡す (spec はハンドルと SettingsView の参照の強さを定めていない): 実装判断として、MAUI の `IScrollController` の実体は持ち主の SettingsView を弱参照で持ち、持ち主が回収された後の命令は何もしない。ViewModel がハンドルをページより長く持っても SettingsView と Native Host を生かし続けないため (Native のハンドルが Host を弱参照で持つのと同じ向き) (2026-09-30)
- Requirement: Host の作り直しをまたぐスクロール位置の保持 (spec は控えられない Host と dispose 時の Host 側の接続を定めていない): 実装判断として、`releaseHost()` で Host が控えを返さない (iOS は view 未読み込み、Android は行が未配置) ときは控えを持たず、次の Host は先頭から表示する。`dispose()` では保持し続けている Host からもハンドルを外す (その Host に積まれた未実行の命令は Native の規則どおり捨てられる) (2026-09-30)

- design Decision 7 (Compose の `AndroidView` の中の View Host の経路): design では「`ViewFactoryHolder` が `saveHierarchyState` で保存し、作り直しで `restoreHierarchyState` する経路にそのまま載る」→ 実機検証 (tasks 6.4) で、Navigation Compose の `NavHost` 配下では位置が戻らないことが分かった。`NavHost` が画面ごとに使う `SaveableStateHolder` は、Activity の保存の後、画面の Composition を破棄するときに同じ画面の状態を保存し直して先の保存を上書きし、その時点の Host は window から外れて行を持たないため、控えの無い状態で上書きされていた。実装では、Host が window から外れる直前に保存状態に載せる控えを取り、外れた後の保存ではそれを使う。既定 id の View Host が複数あるかの判定 (android/ADR-0021) は、外れた後は親をたどれず、外れる時点でも Host が 1 つずつ階層を離れて数え漏れるため、同じ階層の Host がそろっているレイアウトの時点と外れる直前の両方で数えて控える。回帰テストは `ComposeScrollRecreationTest` に `SaveableStateHolder` 配下の Store 方式・DSL 方式・既定 id 複数の 3 件を足した (2026-09-30)
- Requirement: Activity の作り直しで位置を戻す (spec は Activity の作り直し以外で Compose の画面が破棄される場合を定めていない): 上の修正の結果として、`SaveableStateHolder` 配下 (`NavHost` の画面) で、別の画面へ進んで Composition が破棄され、戻って作り直された Compose の `KsSettingsView(...)` も、破棄の前の位置へ戻るようになる (修正前は先頭から表示。Robolectric で `SaveableStateHolder` の key を切り替えて実測、`NavHost` 実機では未確認)。`NavHost` の戻る操作で画面を閉じた場合は保存状態ごと捨てられるので、開き直すと先頭から表示されると推定する (未確認)。Activity の作り直しと同じ保存の経路なので切り分けていない。オーナー合意済み: 別の画面から戻ったときに位置を保つ挙動を受け入れる。理由: Android 標準の一覧 (`LazyColumn`・id を持つ `RecyclerView`) の `NavHost` での振る舞いと、iOS の戻る操作での位置の保持とそろうため (2026-09-30)
- design Decision 8 (Bridge が位置を控える時点): design では「`releaseHost` では、Host を手放す前に `captureScrollAnchor` で控え」→ 実機検証 (tasks 6.4) で、MAUI の Handler の切断 (Pop で消えるページ自身の `DisconnectHandler`) はページの view が window から外れた後に届き、その時点の Host からは位置を控えられないことが分かった (Android は `captureScrollAnchor()` が外れた後の契約どおり `null` を返し、再接続後は先頭から表示。iOS は window の寸法・安全領域を失い、MAUI の View を置いた見出しの高さも変わった後のレイアウトで控えるため、別の要素を控えて途中の違う位置へ戻っていた)。実装では、Bridge が Host を作るときに位置を控え続けるものを Host に付け、`releaseHost()` の時点で Host が window から外れていれば外れる直前の位置を控えとして使う。Android は `KsBridgeHostAnchorTracker.kt` が window に取り付けられている間の描画の直前 (`OnPreDrawListener`) ごとに `captureScrollAnchor()` で控え直す。iOS は `KsBridgeHostAnchorTracker.swift` (Host の view の子に置く見えない view) が、祖先が window から外れる直前 (`willMove(toWindow:)`) に `captureScrollAnchor()` で控える。window に取り付けられたまま手放したときは従来どおりその時点の位置を控える。Native の公開 API (`captureScrollAnchor()` の契約) は変えていない。iOS の `makeHostViewController()` は、見えない view を置くため Host の view を読み込んでから返すようになった (MAUI の Handler は受け取った直後に view を参照しており、読み込みの時点は変わらない)。回帰テストは両 OS の `KsBridgeScrollControlTest(s)` に、window から外れた後に手放す順序のテストを足した (2026-09-30)
- Requirement: 位置を控える・戻す窓口 (spec は window から外れた後を定めていない): iOS の `captureScrollAnchor()` も、Host の view が window から外れた後は `nil` を返す (未実行の位置の復元が待ち行列にあればその控えを返すことを優先する)。理由: Android とそろえ、外れた後の縮んだレイアウト (安全領域の余白が 0・内容の高さが変わる) から見ていた位置と違う要素を返さないため (2026-09-30)
- design Decision 5 (iOS の一方向の着地): design では「推定高さによるずれは、到着後に進行方向と同じ向きでだけ補正する」(UIKit の `setContentOffset(animated: true)` で一度に送る) → 実装では、アニメーション付きの命令を `CADisplayLink` で画面の更新ごとに進め、毎フレーム行き先を最新のレイアウトで求め直して、出発点からその時点の行き先までを進み具合で補間した位置へ送る (進む向きにだけ動かし、行き先は越えない)。到着後の同じ向きの補正はやめ、終了時にアニメーションなしと同じ送り直しで詰める。理由: 実機検証 (tasks 6.3) で、スクロール中に行き先が手前へ移る (推定より低い行が実測で確定して内容が短くなる・MAUI では大きいタイトルの縮小で一覧の表示範囲が伸びる) と、命令の時点の行き先が末尾を越え、同じ向きだけの補正では戻せずに末尾を越えた位置で止まった。UIKit のアニメーションを途中で出し直す形は、出し直すたびに動き出しからやり直して止まりかけるため採らなかった (2026-09-30)
- Requirement: Host への接続と最後の接続 (上の「差し替えで未実行の命令を捨てる」の宣言 UI への適用): DSL 方式の `KsSettingsView` では命令ハンドルが Host ではなく ID を引き直す内部の受け口 (iOS・Android とも `DSLScrollCommandResolver`) に接続するため、`.scrollController(_:)` / `scrollController` 引数でハンドルを差し替えた・外したときは、受け口に残っているまだ引き直していない命令を捨てる。iOS はレビュー指摘 (セカンドオピニオン code-001) を受けて Android の形にそろえた。引き直し済みで Host の待ち行列へ渡った命令は Host 側の扱い (Host の `scrollController` は差し替わらない) のまま残る (2026-09-30)
- Requirement: Host への接続と最後の接続 (上の行の続き): DSL 方式でハンドルを差し替えた・外したときは、受け口に残るまだ引き直していない命令に加えて、受け口が引き直して Host の待ち行列へ渡した未実行の命令も捨て、Host の接続口 (`scrollController` の差し替え・`nil`) と同じ扱いにそろえた。控えた位置の復元 (保存状態からの復元を含む) は捨てない。受け口は Host の未実行の命令を捨てる内部の処理を呼ぶ (iOS は `KsSettingsViewController.dropPendingScrollCommands()` を package に上げ、Android は `KsSettingsView.internalDropPendingScrollCommands()` を足した) (2026-09-30)
- Requirement: スクロール命令ハンドルの公開 (上の「strictMode = false 時のメインスレッド以外からの命令は post して実行する」の補足): post した命令は、命令を出した時点の接続が実行時まで続いているときだけ受け口へ渡す。実行までの間に接続を外した・別の Host へつなぎ替えた場合は、外した接続の未実行の命令として捨てる (接続の差し替えで未実行の命令を捨てる扱いにそろえるため)。同じ受け口への接続し直しは接続を変えない (2026-09-30)
- スコープの拡張 (オーナー指示): 実装フェーズで見つかったスコープ外の 5 件を、起票せずこの change の中で直す。(1) MAUI Android Sample がアクセシビリティ経由の問い合わせ (`AccessibilityNodeInfoCompat.set_Checked` の `MissingMethodException`) でクラッシュする (2) iOS MAUI で Handler の再接続の後に SettingsView の領域が下端まで届かず白い帯が残ることがある (3) Compose DSL の宣言の差分 (`DSLDiffCalculator`) が forEach の途中への 1 項目の挿入で後ろの全項目へ `MoveCell` を出す (4) Android の Compose `KsSettingsView(...)` に文字列の Root Header / Footer が無い (iOS の `.rootHeader(_ text:)` / `.rootFooter(_ text:)`、MAUI の文字列プロパティにそろえた公開 API の追加。Sample の Root Footer もそれに置き換える) (5) iOS Sample の既存画面の Swift 6 concurrency 警告。理由: 同じ実装フェーズで見つかった課題を別 change に逃がさない (2026-09-30)
