# deviation: add-maui-nuget-distribution

実装中に生じた spec / tasks との乖離。spec 本体は書き換えない (逆流修正禁止)。

- tasks 2.2 (Requirement: パッケージの共通メタデータと版集約): tasks では PackageIcon の同梱アイテムを `maui/Directory.Build.props` に置く → 実装では値 (`PackageIcon`) は props、`None Include="assets/icon.png" Pack="true"` の同梱アイテムは `maui/Directory.Build.targets` に置いた。理由: `IsPackable=true` は各 csproj 本体で設定されるため、props の評価時点では `IsPackable` 条件が常に false になり同梱アイテムが効かない。targets なら csproj 評価後に条件が成立する。design Decision 2 の「IsPackable=true のプロジェクトにだけ同梱」は満たしている (2026-09-02)
- Scenario「3 パッケージのローカル pack」(Requirement: 3 パッケージの構成と内容): spec では「facade の nupkg に `.aar` / `.xcframework` / binding の dll が含まれない」 → 実装では facade の nupkg に `lib/net10.0-android36.0/KsSettingsView.Maui.aar` (約 17 KB) が含まれる。理由: .NET Android SDK が Android ライブラリ assembly に対して常に生成する自 assembly 用 aar で、中身は推移依存 `androidx.graphics.path` の ABI 別 `.so` のみ。pack 設定導入前の状態で pack しても同じものが生成されることを実測で確認済み (本変更による混入ではない)。spec の意図である「binding の native 成果物 (`kssettingsview*.aar` / xcframework / binding dll) が facade に混入しない」は満たす。レビュー・verify はこの aar 1 本を違反としない (2026-09-02)
- Scenario「要件の宣言元の一致」(Requirement: 最低 OS 版のビルド時ガード): spec では Android の評価値は「29」 → 実装では SDK が正規化して `29.0` と評価される。理由: .NET Android SDK が `SupportedOSPlatformVersion` を Version 形式に正規化する。宣言元は同梱 props の `29` のままで、`VersionLessThan` 比較は正しく動作する (2026-09-02)
- Requirement「消費者からの導入」/ tasks 6.1: spec では「隔離した packages path とローカルフィードだけを取得元にして行い」 → 消費者検証の `nuget.config` はローカルフィードに加えて nuget.org を残した。理由: `<clear/>` + ローカルフィードのみでは `dotnet new maui` のテンプレート自体が NU1101 (Xamarin.AndroidX.* / Microsoft.Extensions.* 計 14 件が workload の library-packs に無い) で restore できない。隔離した `RestorePackagesPath` は維持し、KsSettingsView 3 パッケージがローカルフィード由来であることは `.nupkg.metadata` の source で確認済み (evidence/consumer-verification.txt)。検証の意図 (本リポジトリの成果物だけが検証対象の取得元になる) は満たす (2026-09-02)
- Scenario「要件未満の利用者アプリ」/ tasks 6.3「未設定の場合も確認する」: spec では「未設定なら … エラーでビルドを止める」 → iOS では `SupportedOSPlatformVersion` 未設定時に SDK の既定値 (26.0 / 26.5) が与えられ要件 16.0 を満たすためガードは発火しない。Android の既定値 21.0 は要件未満なのでエラーになる。理由: .NET SDK は platform TFM に必ず既定値を与えるため、targets の空文字分岐には通常の csproj 記述では到達しない (事実を evidence に明記)。ガードの設計 (空または要件未満で止める) は変えない (2026-09-02)
- Requirement「facade の公開名前空間」(spec が沈黙する利用者可視の変化、オーナー合意 2026-09-02): 名前空間を `KsSettingsView` に改めた結果、`KsSettingsView.SwitchCell` が `Microsoft.Maui.Controls.SwitchCell` と C# 側で衝突し、`using KsSettingsView;` と MAUI の暗黙 using を併用したコードではあいまい参照 (CS0104) になる (XAML の `ks:` prefix では起きない)。指示により受け入れる: 名前空間・型名は変えず、C# から使う場合は完全修飾または using alias が要る旨を README / skills の注意書きとして docs-refresh の依頼事項に含める。理由: 型名変更は公開 API 変更で iOS / Android との命名対称性を崩し、名前空間の決定 (maui/ADR-0025) を覆す価値は無い (消費者検証で観測、evidence/consumer-verification.txt)
- Requirement「facade の公開名前空間」(前項の拡張、review-001 / second-opinion-code-001 で検出、2026-09-02): 名前衝突は `SwitchCell` だけでなく `EntryCell` (`Microsoft.Maui.Controls.EntryCell`) にもある。facade の公開型を列挙して MAUI Controls と同名なのはこの 2 件のみと確認 (`TextCell` / `ImageCell` / `ViewCell` に相当する型は無い)。前項のオーナー決定 (名前空間・型名は変えず注意書き) を同じ理由で両型に適用し、docs-refresh の注意書きは `SwitchCell` と `EntryCell` の両方を対象にする。消費者検証で両型の CS0104 と回避 (完全修飾 / using alias) を実測して証跡に残す
- Scenario「binding パッケージの同梱物と説明」(Requirement: 3 パッケージの構成と内容、review-002 で検出、2026-09-02): spec では「Android binding の `lib/` に aar 2 本」 → 実装では Gradle 由来の 2 本 (`kssettingsview-release.aar` / `kssettingsview-bridge-release.aar`) に加え、.NET Android SDK が自動生成する `KsSettingsView.Binding.Android.aar` の計 3 本が入る。理由: facade の項と同じ SDK 挙動で、中身は推移依存 `androidx.graphics.path` の ABI 別 `.so` のみ (evidence/consumer-verification.txt の名前衝突・XA4301 の節)。spec の意図 (Gradle 成果物 2 本が同梱される) は満たす。レビュー・verify は SDK 生成の 1 本を違反としない
- 公開前の宿題 (review-001 Minor、実装修正なし・オーナー判断待ち、2026-09-02): `assets/icon.png` は AiForms.Maui.SettingsView の `images/icon.png` 由来で公開 3 パッケージに同梱されるが、第三者素材の帰属表示 (LICENSE 内の注記や NOTICE 相当) が無い。原典のライセンス表記を確認したうえで帰属記載を置くか否かは phase-8 (release workflow) の公開前に決める。本 change では記録のみ
