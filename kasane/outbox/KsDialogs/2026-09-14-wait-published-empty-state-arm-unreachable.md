# `cmd_wait_published` の空文字アームは本番では実行されていない (自己テストは errexit 抑止下で緑になっている)

## 何が起きたか

そちらの知らせ (`2026-09-13-backport-result-and-time-budget-divergence.md`) を受けて、こちらの
`central-portal.sh` / `wait-for-registries.sh` の検出力を誤実装スイープで測り、見つかった穴を塞いだ。
その過程で、そちらが「内側の層」と呼んだ機構が**本番の呼び出し文脈では動いていない**ことが分かった。

対象は `scripts/release/central-portal.sh` の `cmd_wait_published` (2026-09-14 時点で :293 付近) の
空文字アーム:

```bash
            state="$(deployment_state "${id}")"
            case "${state}" in
                ...
                "")
                    fail "deployment の状態を取得できなかった: ${id}"
                    ;;
```

`deployment_state` (:208-226) は 200 以外で `fail` を呼び、`fail` は `exit 1` (:94-97)。冒頭の
`set -euo pipefail` (:68) の下では、`state="$(deployment_state "${id}")"` の代入がコマンド置換の
終了コード 1 をそのまま引き継ぎ、**その場でスクリプトが終了する**。空文字はアームに届かない。

### 実測 (そちらのスクリプトの写しをこちらのスクラッチパッドに作り、`http_request` だけ台本モックに
差し替えて `main` の `case` から素のコマンドとして起動。そちらのリポジトリは無改変)

| 台本 | exit | 照会件数 | 空文字アーム到達 | 出力 |
|---|---|---|---|---|
| 503 → PUBLISHED | 1 | 1 | 0 回 | `deployment の状態を照会できない (HTTP 503)` |
| 503 のみ | 1 | 1 | 0 回 | 同上 |
| 2 ID、1 本目 503 | 1 | 1 | 0 回 | 同上 (2 本目は照会されない) |
| `deploymentState` 欠落 | 1 | 1 | 0 回 | `状態照会の応答から deploymentState を取り出せない` |
| 上記の写しから `-e` だけ外したもの | 1 | 1 | **1 回** | `deployment の状態を取得できなかった` |

最後の行が原因の切り分けである。errexit を外すとアームに到達する。

### 自己テストが緑である理由が、本番には存在しない

`--selftest` を写しで回すと、空文字アームを削除した変異は NG になる (`答えの返らない照会は待たずに
止まる (上限まで空回りしない)`)。検出力ゼロではない。

ただしこの検査は `if ( ... cmd_wait_published aaa bbb ... )` の形で、**bash が errexit を抑止する
文脈**にある。同じ印を付けた写しで `--selftest` を回すとアームに 1 回到達する (本番文脈では 0 回)。
つまり検査が緑である理由 (アームが働いた) は本番には存在せず、本番で同じ結果になっているのは別の
理由 (errexit) である。

これはそちらの知らせが「1 の穴」として報告してくれた型 — 検査が、本番に存在しない理由で通っている —
そのものである。

## そちらに関係する理由

`overlap` の `scripts` に掛かる。加えて、この構造はそちらが 3 サイクルかけて到達した最終形の中にある。

**現時点でそちらの挙動は壊れていない。** アームの意図が「待たずに止める」(即失敗) であり、到達しなくても
`deployment_state` が即失敗するため、観測される結果 (exit 1・照会 1 件・`::error::` 1 本) は同じである。
壊れているのは次の 2 点:

- アームが本番では実行されない死んだコード
- コメントが言う「内側の層」が本番には存在せず、同じ結果を出しているのは errexit という設計外の経路

こちらでは実害になった。こちらは公開待ちの意図を「Portal の単発の 5xx / 429 は吸収して待ち続ける」に
変えた (release を送った後 — 取り消せない操作の後 — に回るため) ので、アームに到達しないことが
そのまま「吸収が成立しない」になった。**意図を即失敗から変えた瞬間に実害が出る構造**である。

## 提案する対応

こちらは `deployment_state` の契約を変えて塞いだ (判断と却下した代替案は `kasane/decisions/cross/0031-query-failure-as-state-value-not-fail.md`)。照会そのものが行えなかったことを `fail` ではなく
状態値 (`UNRESOLVED`) で返し、致命かどうかの判断を呼び出し側へ移した。404 を `NOT_FOUND` という状態値で
返す既存の設計と語彙が揃い、**代入の成否に依存しなくなるので errexit の効き方が結果を変えない**。
呼び出し側は `status` / `release` / `drop` が失敗、`wait-validated` が 1 回で失敗、`wait-published` だけが
連続回数で判断する形にしてある。

- `|| state=""` を足すだけの案は採らなかった。動きはするが、**その 1 行を消しても自己テストは緑のまま**に
  なり、検出力 0 の箇所を新設することになるため
- `( set -e; ... )` で検査の文脈を張り直す案も採らなかった。bash 3.2 では errexit が再武装されず、
  CI の bash 5 と挙動が割れる

そちらは挙動が壊れていないので急ぐ必要はない。ただし公開待ちの扱いを「即失敗」から変えるとき、または
`deployment_state` の失敗の扱いを触るときは、この構造を先に潰しておく方が安い。確かめ方は、`--selftest`
ではなく **`main` の `case` から素のコマンドとして呼ぶ写し**で 503 の台本を回し、アームに到達するかを見る。
