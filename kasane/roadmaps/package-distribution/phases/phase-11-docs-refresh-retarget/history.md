# phase-11-docs-refresh-retarget 議論履歴

## 2026-08-25: 2 言語の生成方式

論点の中で最上流 (差分更新の単位・生成プロンプト・整合性チェックの形を規定する) として最初に議論した。前提は phase-10 確定の翻訳ロックステップ (en/ja 同一構成・同時更新、manifest targets は言語抜きパス)。

選択肢:
- A: 英語を正として書き、日本語は英語から翻訳して派生 — concepts が日本語のため日本語版が「日本語→英語→日本語」の往復翻訳になり劣化リスク
- B: 同一サブエージェントが concepts から en/ja を同一文脈で同時生成 — 構成・コード例の一致が生成時点で保証、日本語版も concepts から直
- C: 言語ごとに別作業者が独立生成 — 最速だが両版の乖離が事後チェック頼み

採用: **B**。理由: ①正本 concepts が日本語であり両言語とも直に書ける、②コード例は言語版間で完全同一であるべきで、同一文脈生成ならロックステップが「検出する」ではなく「構造的に破れない」ものになる。作業単位は「言語ペア 1 組 = 1 タスク」が基本形。

ADR 化は見送り (docs-refresh スキル内部の手順選択で、可逆・局所的。ロックステップ規約自体は ADR-0022 が既に保持)。

## 2026-08-25: 初期生成の分担 (対象の切り替えの残り論点)

対象の切り替え・manifest v3 の形は phase-10 で確定済みのため、残る実質判断「skills/ 未生成状態からの初期生成をどちらが担うか」を議論した。

選択肢:
- A: docs-refresh は差分更新専用、初期生成 (skills/ 一式 + manifest 初期版) は phase-12 の change が担う — 創作 (能力マップ・レシピ設計・配置判断) は変更フロー、機械追従はスキル、と責務分離
- B: docs-refresh --all で初期生成も可能にする — ツール 1 本で完結するが、manifest 生成ロジックを内蔵して肥大化し、--all が 2 つの意味を持つ

採用: **A**。帰結: manifest 不在・破損時はフォールバック再生成せず停止して phase-12 (初期生成) を案内。`--all` = manifest 前提の全再生成。旧 docs/.manifest.json・docs/ の削除は phase-12 の作業。phase-11〜12 間のギャップ中は docs-refresh 実行不能 (許容)。

ADR 化は見送り (フェーズ間の作業分担で、決定は proposal / tasks に反映されれば足りる)。

## 2026-08-25: 差分更新フローの細部 (機械チェックとフラグの引き継ぎ)

現行 Step 2e のコード正の機械チェック 3 種 (モジュール一覧 / Sample デモ画面一覧 / ツール最低バージョン) について、削るか突合先を付け替えて維持するかを議論した。

採用: **維持して突合先を README 群へ付け替える**。モジュール表・対応表はルート README 群 (README.md / README_ja.md)、デモ一覧は samples/*/README.md のみ (Skill はレシピ形式でデモ一覧を持たない想定)、ツールバージョンは README 対応表 + SKILL.md 導入節に記載がある場合はそこも。源泉がコードのため manifest には載せずスキル本文の手順として持つ (manifest の源泉は concepts のみ、ADR-0022 と整合)。フラグは `--all` = manifest 前提の全再生成 (既決)、`--readme-only` = readmes 列挙分のみの軽量チェックとして維持。

ADR 化は見送り (スキル内部の手順で可逆・局所的)。

## 2026-08-25: サブエージェント委譲の単位

「メインは concepts 本文を読まない」原則と委譲方式の維持を前提に、委譲の粒度を議論した。

選択肢:
- A: Skill 単位 — 1 Skill の更新対象ファイル群 (両言語) を 1 タスクに。能力マップ (SKILL.md) とレシピ (references) の整合が同一文脈で保証される
- B: ファイルペア単位 — 並列度は高いが、Skill 内の整合 (レシピ追加が能力マップに反映されない等) が事後チェック頼みになる

採用: **A**。2 言語生成で同一文脈ペア生成を選んだのと同じ判断構造 (整合はチェックで検出するのではなく構造で保証する)。README 群は対象 README ごと (en/ja ペアがあればペア)。並列上限は現行の最大 3 並列バッチを据え置き。プロンプトテンプレート本文は ksn-propose で確定。

ADR 化は見送り (スキル内部の手順で可逆・局所的)。

## 2026-08-25: 整合性チェックの一式とコード例のコメント規約

v3 の機械検査一式 (網羅検査 / en/ja 節構成一致 / コードブロック一致 / frontmatter / 旧名残 grep / リンク解決 / ローカル絶対パス / 識別子表記ゆれ) を提示し、設計判断が要る「コード例内コメントの言語」を議論した。

提示した選択肢は「コメントを言語版ごとに翻訳 (検査はコメント行除外一致)」と「コード例完全同一 (コメント英語統一・byte 一致検査)」。ユーザーから第 3 の方向「そもそもコード例に極力コメントを書かないのが良いのでは」が出た。一度この案を確認前に決定扱いしてしまい、ユーザーの指摘で論点に差し戻して再提示した経緯がある (決定の発火はユーザーの採用宣言のみ、質問は発火条件ではない)。再提示のうえで採用が確定:

- コード例は原則コメントレス。説明はレシピ形式の見出しとリード文が担う (段階開示の設計原理と一貫)。生成プロンプトの制約に明記する
- やむを得ない最小限のコメント (省略プレースホルダ等) は英語統一
- 帰結として en/ja のコードブロックは byte 一致検査 (最強・最単純) が成立する

ADR 化は見送り (スキル内部の検査手順とコンテンツ規約の細部。内容規約の大枠は ADR-0022 が保持)。

## 2026-08-25: 起動規律と AGENTS.md / CLAUDE.md の更新タイミング

自動発動禁止の引き継ぎは確定済み制約の踏襲として無議論で維持。AGENTS.md の古くなる記述 (「docs/ は利用者向けドキュメント」「docs/ と README 群の書き換えは docs-refresh 経由のみ」) の更新タイミングを議論した。

選択肢: A: phase-11 で書き換え + docs/ 凍結注記 / B: phase-12 でまとめて更新 (ギャップ中は記述と実態が食い違う)。

採用: **A の変形** — phase-11 の change で「skills/ と README 群は docs-refresh 経由のみ」へ書き換え、docs/ への言及は除去する。ただし凍結注記は置かない (ユーザー判断: docs/ は phase-12 で完全削除されるため、ギャップ中の保護をわざわざ宣言する必要はない)。

ADR 化は見送り (リポジトリ規約ファイルの記述更新で局所的)。
