## Context

検証 CI が何をもって「通った」とするかを決める必要があった。テストの実行形態には、ロジックだけを検証する形と、実際の画面と実行環境を起動して挙動を確かめる形がある。

このライブラリは UI コントロールを提供し、利用者から見える価値の多くは実行時の描画・入力・タイミングにある。したがって実行時の確認は品質保証に不可欠であり、実際に規約として「利用者の目と操作に見える変更は実機または Simulator での確認を完了条件にする」を持つ。

一方、実行ホストを起動する検証を CI に載せると、Simulator / Emulator の起動時間と、環境要因による不安定さ (同じコードでも実行機の負荷で結果が変わる) を毎回の pull request が負担する。

MAUI 側には検証ホストを起動して確かめる手順が別途あり、iOS には Simulator 上でテストを実行する形が既にある。両者は性質が異なる — 前者は人が画面を見て判断し、後者は自動で成否が決まる。

## Decision

CI の緑が意味するのは「**ロジックが全件通過し、native への配線がコンパイルできる**」までとする。

- 自動で成否が決まるテストは CI で全件実行する。iOS は UIKit を要するテストを含めて実行できる形 (Simulator を対象とする実行) を採り、ホスト上でロジックだけを実行する形は成否判定に用いない
- 実行ホストを起動して人が確かめる検証 (MAUI の検証ホスト実行) は CI に載せず、手元の手順として残す
- テストが 1 件も実行されなかった場合は、テスト自体が緑でも失敗として扱う。実行件数の確認までを検証とする既存の規律を、CI の成否判定に組み込む

利用者の目と操作に見える変更に対する実機・Simulator での確認は、CI とは独立に、従来どおり変更の完了条件として残る。CI はこれを代替しない。

## Alternatives Considered

- **実行ホストの起動を含む検証まで CI に載せる** — 却下。Simulator / Emulator の起動時間と環境要因による不安定さを毎回の pull request が負担することに、得られる保証が見合わない。実行時の確認は変更の完了条件として別途担保されている
- **iOS でホスト上のロジック実行を成否判定に使う** — 却下。UIKit を要するテストが除外され、テスト全体の一部しか実行されない。緑の意味が「一部だけ通過」に薄まる
- **実行件数を確認せず、テストの成否だけで判定する** — 却下。テスト探索の破綻でテストが 1 件も実行されなくても緑になり、検査が無いのと同じ状態が緑として報告される

## Consequences

- 正: 毎回の変更に対して短い時間で結果が返り、環境要因による不安定さを最小限に抑えられる
- 正: 「緑が何を保証しないか」が明示されるため、実行時の確認を CI で代替できるという誤解が生じにくい
- 正: テスト探索の破綻が緑として報告される経路を塞げる
- 負: 実行時にしか現れない欠陥 (描画・入力・タイミング) は CI では捕まらない。これらの検出は変更ごとの実機確認に依存し続ける
- 負: 実行件数の検査を platform ごとに実装する必要があり、テスト結果の出力形式が変わると検査も追随を要する
