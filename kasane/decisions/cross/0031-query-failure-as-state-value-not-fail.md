## Context

`scripts/release/central-portal.sh` は Maven Central Portal の deployment を照会し、状態に応じて待機・release・drop を行う。照会を行う `deployment_state` は当初、404 だけを状態値 (`NOT_FOUND`) で返し、それ以外の異常 (通信失敗・5xx・応答から状態を取り出せない) を `fail` で表していた。`fail` は `::error::` を出して `exit 1` する。

この設計は、呼び出し側がコマンド置換で結果を受ける形と噛み合わない。`fail` の `exit` はコマンド置換のサブシェルしか終わらせないため、呼び出し側に届くのは空文字である。そこで待機関数の側に「空文字が届いたときの分岐」を置くことになるが、**その分岐に到達するかどうかは errexit の効き方で決まる**。

- 本番は `main` の `case` から素のコマンドとして呼ばれる。冒頭の `set -euo pipefail` が効くため、`state="$(deployment_state "${id}")"` の代入がコマンド置換の終了コードを引き継ぎ、その場でスクリプトが終了する。空文字の分岐には到達しない
- 自己テストは検査を `if ( ... )` の条件部で呼ぶ。bash はこの文脈で errexit を抑止するため、空文字が分岐へ届く

結果として、**空文字の分岐は自己テストでだけ実行され、本番では死んでいる**。この非対称は実測で確認した。台本 (1 件目 503、2 件目 PUBLISHED) を与えると、本番文脈では exit 1・照会 1 件で終わり、errexit だけを外した写しでは分岐に到達する。

この構造は兄弟リポジトリ KsDialogs にも存在する。あちらは分岐の意図が「待たずに止める」(即失敗) であり、到達しなくても `deployment_state` が即失敗するため観測結果が変わらず、露見していなかった。こちらは公開待ちの意図を「Portal の単発の 5xx / 429 は吸収して待ち続ける」へ変えた時点で、分岐に到達しないことがそのまま機能の不成立になった。公開待ちは `release` を送った後 — 取り消せない操作の後 — に回る位置にある。

## Decision

`deployment_state` は、**照会そのものが行えなかったことを状態値 `UNRESOLVED` で返す**。`fail` は使わない。404 を `NOT_FOUND` で返す既存の設計と同じ語彙になる。失敗の理由 (HTTP ステータス、要求が失敗したこと、応答から状態を取り出せなかったこと) は注釈ではなく標準エラーの素の行として出し、`::error::` の注釈は致命と判断した呼び出し側が出す。

**致命かどうかは呼び出し側が決める。** 照会の結果を受ける 5 経路の扱いは次のとおり。

| 呼び出し | `UNRESOLVED` の扱い |
|---|---|
| `status` | 失敗 |
| `release` | 失敗 (POST は送らない) |
| `drop` | 失敗 (DELETE は送らない) |
| 検証の決着待ち | 1 回で失敗 |
| 公開待ち | 連続して許す回数まで吸収し、超えたら失敗 |

公開待ちだけが吸収するのは、`release` を送った後に回る位置だからである。吸収した照会は「何回目まで許したか」を 1 行出し、諦めるときの理由には経過を添える。取り出せた照会を挟めば連続の数は戻る。

この形の眼目は、**照会の失敗の扱いが errexit の効き方に依存しなくなる**ことにある。代入の成否ではなく返った値で分岐するため、自己テストの検査文脈と本番の呼び出し文脈が同じ経路を通る。

## Alternatives Considered

- **代入に `|| state=""` を足して errexit から切り離す**: 却下。本番文脈での吸収が成立することは実測で確認したが、**その 1 行を消しても自己テストは緑のまま**になる。検出力の無い箇所を新設することになり、この変更が潰していた型 (検査が本番に存在しない理由で通っている) を 1 つ作って終わる。
- **自己テストの検査を `( set -e; ... )` で囲み、本番と同じ errexit 文脈を張り直す**: 却下。bash 3.2 では errexit が再武装されないことを実測した。開発機と CI で bash の版が割れると、検査の意味そのものが環境で変わる。
- **待機関数を allowlist 型にする (継続する状態を列挙し、未知はすべて失敗)**: 却下。空文字は確かに弾けるが、Portal が状態名を足した時点でリリースが即失敗する。未知の非空状態は上限まで待つ方が安全側に倒れる。
- **公開待ちも 1 回で失敗させる**: 却下 (オーナー裁定 2026-09-13)。再実行で復旧はできるが、取り消せない `release` の後で単発の 5xx に落ちる。同じ経路の `wait-for-registries.sh` が逆の方針 (判定不能でも待機は続ける) を明示しており、その非対称に理由が無い。

## Consequences

- 正: 照会の失敗の扱いが errexit の効き方に依存しない。自己テストの検査文脈と本番の呼び出し文脈が同じ経路を通るため、検査が本番を代表する。
- 正: 404 と照会不能がどちらも状態値になり、`case` で並べて読める。
- 正: 致命かどうかを呼び出し側が持つため、経路ごとに違う扱い (公開待ちだけ吸収する) を書ける。
- 負: 照会の結果を受けるすべての経路が `UNRESOLVED` を扱う責任を持つ。見落とした経路では、致命が状態として素通りする。
- 負: 失敗の理由は状態値に乗らないため、標準エラーへ別に出す必要がある。呼び出し側が注釈を出すかどうかも経路ごとの判断になる。

## Revisit When

- Portal の API が照会の失敗を状態として返すようになったとき — 状態値への畳み込みが二重になる
- 自己テストの実行環境の bash が版で固定され、検査文脈で errexit を張り直せるようになったとき — 却下した代替案の前提が変わる
- 公開待ち以外にも吸収が必要な照会が現れたとき — 吸収を経路ごとに書く形が保てるか見直す
