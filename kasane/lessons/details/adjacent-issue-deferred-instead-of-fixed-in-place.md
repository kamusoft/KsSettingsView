## 統合前のルール文 (候補)

探索・提案・レビュー対応で、今の change が触る機構 (同じ View 階層・同じ優先度設定・同じ解決関数・同じ bind 経路など) の中に隣接する課題を見つけたら、次のどちらかに当たる限り、別 change の簡易起票や Non-Goal への明記で切り離さず、本 change の What Changes とデルタスペックに含める: (a) 同じファイル・同じ機構の修正で直る、(b) 今の change の契約を閉じるのに必要 (例: 「icon 枠は譲らない」は「足りないとき誰が譲るか」が決まって初めて閉じる)。切り離してよいのは独立した機構・別の設計判断・別 platform の別問題に限り、そのときは Non-Goals に切り離す理由を 1 行で書く。事後判定: proposal の Non-Goals に「同じ機構の課題を後続 change へ」という項目が無く、隣接課題が specs / tasks に反映されている。

## 関連

昇格済みの process L-005 (数行で閉じる修正を別 change へ逃がさない) と同根。L-005 は実装・レビュー対応フェーズで「数行で閉じるか」を基準にするのに対し、本パターンは探索・提案フェーズで「同じ機構か / 契約を閉じるのに必要か」を基準にする。昇格時は L-005 への統合 (適用フェーズと判定基準の拡張) を第一候補にする。

- 2026-09-01 fix-ios-test-pump-condition-wait: 置換 206 箇所のうち 1 箇所で、テストが主張していた「無効化しないと追従しない」が実際には「その瞬間には追従しない」でしかないと判明した。ホストは対応案を 3 つ出したが、実挙動に合わせて書き直す案にだけ「本 change のスコープ (待ち方だけを変える) を超える / 別 change 相当」という注記を付けた。オーナーは注記ごと却下して本 change での対応を指示。書き直しは同一ファイル・同一機構の中で閉じ、プロダクトコードの変更も不要 (doc コメント 1 箇所のみ) だった。**選択肢に「別 change 相当」と書く前に、その修正が同じ機構の中で閉じるかを先に確かめる** — 注記そのものがオーナーの判断を歪める材料になる。
- 2026-10-04 align-toolchain-xcode27-jdk21-dotnet-10-0-401: 新しい開発機の環境に合わせる S 級の変更。(1) 探索で、旧い開発機の場所を指す Android SDK の設定を見つけたが、git 管理外であることを理由に「今回の変更には含まれず、手元で直す必要がある」と報告した。オーナーは「これも修正するべきだろう」と戻した。(2) 実装後、iOS 27 の Simulator で毎回落ちるテスト 1 件について、ホストは「原因が版合わせの外にある」として別 change の起票を推奨した。オーナーは本 change に含める方を選び、調べるとテスト 1 件の書き直しだけで閉じ、本体の変更も設計判断も要らなかった。(3) 完了報告で、テスト失敗時に診断収集で約 10 分待つ件を「スコープ外で見つかったもの。起票するかはお任せ」と載せた。オーナーは「これは今やっとこう」と戻し、workflow の 3 行で閉じた。3 件とも、**環境を替えたことで初めて表に出た不具合で、その環境へ合わせること自体が本 change の目的だった**。「差分が原因ではない」ことは切り離す理由にならず、変更の目的 (新しい環境で通る状態にする) を満たすのに要るかで判定すべきだった。
