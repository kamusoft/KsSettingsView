# reachable-fix-deferred-to-another-change (process L-005 の経緯)

inbox パターンとして pain 4 件で閾値到達し、2026-08-22 にオーナー承認で `process.md` L-005 へ昇格した。

## 経緯

- 2026-08-01 fix-cell-accessory-vertical-fill: 実装フェーズ完了報告で、オーケストレーターが 2 件をオーナー判断事項として上げたが、2 件ともその場での修正を指示された。
  1. **valueText とアクセサリの間隔 6pt → 16pt**: 「spec が spacing を対象外と明記しており規約違反ではない。現状維持を望むなら視覚パラメータの変更として別 change 相当」と報告 → オーナー「これくらい change 相当じゃなくて今できるはず」。実際 `stackH.setCustomSpacing(_:after:)` 1 行で済む修正だった。
  2. **触れたファイルに残る既存コメント規約違反 5 箇所**: レビュアーの Minor が「触れたブロックのみ」と限定していたこと、リポジトリ全体には同種違反が 91 ファイルあることを理由に「スコープ外・別 change 候補」と報告 → オーナー「触れたファイルの部分だけ直す」。触れたファイルは 14 個で、そこに閉じた掃除は本サイクルで完結できた。
- どちらも判断材料 (規約違反かどうか / レビュアーの指摘範囲) は正しく、結論だけが保守的すぎた。**「規約違反ではない」は「直さなくてよい」ではない**。オーナーに上げるコスト (往復1ターン + 判断負荷) が、その場で直すコストを上回っていた。
- 91 ファイルへの全体展開を断ったこと自体は支持された — 切り分けの線が「触れたファイルの内か外か」であり、「規約違反か否か」ではなかったのが誤り。
- 2026-08-21 upgrade-android-build-toolchain: `android/gradle/libs.versions.toml` を新設してバージョンの SSoT を移したのに、MAUI binding csproj の aar 再生成判定 (`KsAndroidModuleSource`) にその toml が入っていない問題を、実装ワーカーの「スコープ外の発見」と相方レビューの Major が共に検出。オーケストレーターは proposal の Non-Goal「csproj は変更しない」を理由に簡易起票を提案 → オーナー「そんなことでいちいち簡易起票せずにすぐに対応して」。実際は csproj に 3 行追加で閉じる修正で、本 change の変更 (SSoT 移設) が直接の原因だった。**Non-Goal は「その領域の改修をしない」宣言であり、本 change が自分で開けた穴を塞ぐことまで禁じていない**。
- 2026-08-22 harden-compose-settingsroot-dsl: 相方レビューが未追跡の `android/.kotlin/` (Kotlin 2.x のビルド生成物が `.gitignore` に無い) を補足として挙げた。オーケストレーターは「本 change の成果物には含めない」と切り分けたうえで「スコープ外の既存不備なので後ほど簡易起票を提案」と報告 → オーナー「こんなことでいちいち起票せんでいい、今対応できるだろう。スコープ内だろ、これは」。実際は `.gitignore` に 1 行追加で閉じた。
- 2026-08-22 fix-ios-entrycell-writeback-race: ゲート不成立の裁定伺いに「スコープ外の発見3件」(再現スクリプトの既定注入速度・サンプル画面のラベル伸長・一時作成した実機ドライバの残置可否) を添えて簡易起票を提案 → オーナー「簡易起票いらん」。この 3 件は前 3 例と違い**その場で直すべき数行の不備ですらなく、報告に載せる価値自体が無かった**。上げる / 直すの二択の手前に「そもそも報告に載せるか」の閾値がある。
- 4 例に共通するのは、**切り分けの線を「本 change の proposal / spec が対象と宣言した範囲か」に引いていた**こと。オーナーが引いている線は「今のサイクルで数行で閉じるか」であり、成果物として commit される作業ツリーに現れた不備は、proposal が名指ししていなくても本サイクルの守備範囲に入る。判断を上げる前に「修正が数行で閉じるか」を先に見積もる。
