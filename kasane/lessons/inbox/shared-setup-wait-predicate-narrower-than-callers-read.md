## ルール文 (候補)

複数のテストが共有する setup ヘルパの待機述語は、**そのヘルパを呼んだ直後に呼び出し側が読む対象の和**で書く。ヘルパの代表的な用途 (先頭 Section の item 0 等) だけを述語にすると、supplementary や 2 番目以降の Section を読む利用者では収束前の状態を検証することになる。条件を絞ってよいのは「そもそも生成されないもの」(表示領域外の行など) に限り、「たまたま今の呼び出し側が読まないもの」を外さない。

**狭い述語と広い述語を併存させない。** 選べる余地があると狭い方が使われ続ける (上記の事例では広い版が既にあったのに 5 箇所が狭い版のままだった)。広い版に一本化し、狭い版は削除する。

固定時間待機を条件ベース待機へ置き換える作業で特に起きやすい。待機の作り (実時間 deadline・ループ内で実行機会を譲る・超過時は実測値付き fail) が規約どおりでも、**述語の射程が狭ければ「待ったつもり」は残る**。個々の呼び出し箇所の述語は分類台帳を見ながら 1 件ずつ選ばれるのに対し、setup ヘルパの述語は 1 つ書けば全利用者に効くぶん、利用者側の読み取り対象と突き合わせる工程が抜け落ちやすい。

事後判定: 共有 setup ヘルパの待機述語が、全呼び出し側が直後に読む対象 (Cell / supplementary / Section) を含んでいる。同じ役割の狭い版が併存していない。

**個別に潰さず、機械的に洗う。** この型は 1 箇所直しても別インスタンスが残る (下記の事例では修正サイクル 2 周連続で同じ型が Major になった — 1 周目は section の header / footer、2 周目は Root accessory の取りこぼし)。共有述語を直すときは次を工程に入れる:

1. 対象の種別 (supplementary の elementKind 等) を**コードから全列挙**する — 記憶や代表例で書かない
2. 共有述語の**全呼び出し経路**を列挙し、それぞれが待機直後に読む対象と突き合わせる
3. **退化した構成** (Section 0 件・行 0 件・supplementary のみ等) で述語が素通りしないか確認する。早期 return する guard は「待つべきものが本当に無い」ことを保証しているか
4. 種別を後から足したときに、述語の更新漏れが**壊れたと分かる**形にできないか検討する

## 経緯

- 2026-09-01 fix-ios-test-pump-condition-wait: 呼び出し 206 箇所の置換自体は述語の質が高く (更新前から真の不変条件を述語にしない、という規則が守られていた)、レビューも「個々の置換の述語の質は高い」と評価した。欠陥は setup ヘルパ 1 つに集中しており、そこだけが全利用者に波及する構造だった。修正では述語を「全 Section の行数一致 + 表示領域にかかる全行の Cell 実体化 + 全 Section の header / footer supplementary の実体化 (領域が可視のときのみ)」まで広げ、共有ターゲットに単一定義として置いて狭い版を削除した。なお、この修正の実効性は**手元の Simulator では pass/fail に現れない** (述語を常に真にしても全件通る — 初期反映が同期完了するため) ことが mutation 実験で判明しており、効くのは実行機が混雑した CI 上である。**手元で通ることは、待機が正しく書けている根拠にならない**という規約 (`kasane/handbook/cross/test-execution.md`) がヘルパ自身の検証にも当てはまる。
- 2026-09-01 (同 change の修正サイクル 2 周目): 1 周目の修正で述語を広げた際、section の header / footer は網羅したが **Root accessory の kind が漏れた**。さらに可視 Section 0 件の構成では guard が早期 return して RunLoop を 1 度も回さず、**置換前の固定待機 0.05 秒より待ちが短くなる**箇所が生まれていた (同じ change 内に Root 用の述語が別途あったにもかかわらず)。同じ型が 2 周連続で Major になったことが、この教訓を「個別の指摘への対応」ではなく「網羅の工程」として書くべき根拠になっている。なお、どちらの周も**全件テストは緑のまま**であり、手元の pass/fail はこの欠陥をまったく検出しない。
