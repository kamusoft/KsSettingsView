# ソースコメント規約

この文書は、リポジトリ内の全ソースコード (Swift / Kotlin / C# ほか) のコメントに何を書いてよく、何を書いてはいけないかを定める。読むと、コメントに使える外部参照の種類と、禁止パターンを見つけたときの書き換え方が分かる。

コメント (doc comment / 行コメント / ブロックコメント / `// MARK:` 等の区切りコメントを含む) は、**そのファイルだけを読んでいる人 (人間・エージェント双方)** にとって意味が通ることを最低条件とする。文脈依存の参照や履歴記述はコードのノイズであり、コメントの信頼性を損なう。

## 許容する外部参照

リポジトリ内のコード識別子 (型名・メソッド名・ソースファイル名) への参照は外部参照ではなく、自由に書いてよい (grep で到達でき、消えれば同一コミット内で壊れに気づけるため)。それ以外にコメント中で参照してよい外部識別子は以下の3種のみとする。

- **`<domain>/ADR-NNNN`** — `kasane/decisions/<domain>/NNNN-*.md` に確定した設計判断への参照 (例: `cross/ADR-0017`)。`<domain>` は `kasane/decisions/` 直下のディレクトリ名
- **URL** — 恒常的に到達可能な公開文書 (公式ドキュメント・仕様書・RFC 索引など)
- **RFC 等の恒常的規格** — `RFC 6749` のような業界標準の識別子

## 禁止する参照

以下の外部識別子はコメントに書かない。

- **変更提案の識別子の裸参照** (`align-sample-parity` `本提案 add-partial-update-core` `purify-core-extract-style-to-ui-layer Decision 5` 等) — 変更 (change) は作業単位でありアーカイブ後に文脈を追えない。ADR に対応があれば `<domain>/ADR-NNNN` へ置換する
- **Phase / Round / Decision / Critical / Major / Minor / 論点 / 案 番号** (`Phase 18` `Phase 15.1` `Round 2` `Decision 5` `Major-1` `論点 23` `案 β` 等) — レビュー通番・議論プロセスのローカル通番・仮称であり、アーカイブ文書に依存する
- **変更アーティファクト内のタスク通番** (`タスク 2.4` `タスク 5` `task 3` 等) — tasks.md の通番であり、アーカイブ文書に依存する。対象は直後に数字を伴う形のみで、「タスクを 3 回実行する」のような一般語用法は含まない
- **アーカイブ文書のパス / 行番号** (`openspec/changes/.../spec.md` `design.md` `proposal.md` `review-result_002` `review-001.md` `spec.md L107` 等) — `openspec/` は凍結済み歴史資料、`kasane/changes/` の文書はアーカイブされる作業資料であり、指す先の意味を後から追えない
- **拡張子なしの裸参照** (`cell-types-basic spec` `delta spec Requirement「〜」` `spec L31-32` 等。delta spec = `kasane/changes/*/specs/` に置かれる変更提案内の仕様差分文書) — 拡張子や URL を伴わないアーカイブ文書への裸参照も同じく禁止 (`.md` を書かなくても意味は同一で、grep で検出しづらいだけ)。ADR に対応がなければ自己完結する説明に書き直す

## 禁止する記述類型

以下の記述はコメントに書かない。

- **進捗ログ・履歴記述** — 「〜で新規追加」「全面刷新」「旧実装を撤去」「旧方式は〜」「〜から移植」「〜へ移行」など、時間軸を含む記述はコメントの仕事ではない (git 履歴の責務)
- **アーカイブされた過去仕様の説明** — 「旧 X は〜だった」ではなく、現在の仕様を現在形で書く
- **デルタスペック構文キーワードの混入** (`MUST` `MUST NOT` `SHALL` `SHOULD` `SHOULD NOT` `MAY` 等) — これらは delta spec の Requirement / Scenario 記述用のキーワードであり、実装コードのコメントに残すべきではない。規範性は自然な日本語 (「〜する」「〜してはいけない」「〜必須」「〜任意」等) で表現し、コメントは通常の日本語説明文として自然に読める形にする。根拠の参照が必要なら `(<domain>/ADR-NNNN)` を添える
- **レビュー指摘・議論の通番** (`review-result_002 Major-1` `C-1` `Decision <数字>` 等) — 変更提案内の通番であり、アーカイブ後は元文書を追わないと意味が取れない

## 移植元 AiForms への言及

移植元 ([移植元 AiForms リポジトリの参照](aiforms-origin-reference.md) — 移植完了時に失効する時限規約) との互換仕様は、**現在形の仕様説明**として書くのは許容する (例: 「AiForms.Maui.SettingsView と同じく `Checked` は OneWay」)。これは「今この実装が守っている互換契約」の記述であり、履歴記述ではない。一方「AiForms から移植した」「旧 AiForms では〜だった」のような時間軸・過去仕様の記述は、上の禁止類型どおり書かない。

## 書き換え時の判断基準 (3 類型)

既存コメントに禁止パターンが混入している場合、以下 3 類型のいずれかで書き換える。

1. **定型句型** (`// 仕様: openspec/changes/.../spec.md` `/// 〜を検証する (Phase 17)` など、参照が装飾で本文と独立している):
   - 参照句を削除し、残る説明が自然に読めるよう整形する

2. **理由一体型** (参照タグと設計理由が一体化しており、単純削除すると文意が壊れる):
   - 意味的に対応する ADR が `kasane/decisions/` にあれば `<domain>/ADR-NNNN` 参照に置換する
   - 対応する ADR がなければ、コメント内で自己完結する設計説明に書き直す
   - **書き換え作業の中では新規 ADR を起票しない** (ADR 化に値する判断は変更フローの中で既に起票済みという前提を置く。「これは ADR にすべきでは」と迷う判断に出会ったら、勝手に起票せずオーナーに確認する)

3. **履歴記述型** (「旧方式は〜」「〜で撤去された」など、過去の仕様を語っている):
   - 現在の仕様の説明に書き換えるか、情報価値がなければ削除する
   - 例: 「旧 `AnyCell` 型消去ラッパは廃止された」→ 「`Section` は `any KsCell` の配列を直接保持する」

## 適用範囲と運用

- 対象: リポジトリ内でコメント構文を持つ全ファイル (`*.swift` `*.kt` `*.cs` のほか、ビルドスクリプト・XML レイアウト等も含む。テストコード・Sample アプリも含む)
- 対象外: `openspec/` 配下 (凍結済み歴史資料)・`kasane/` 配下のドキュメント (独立した規約体系)・`skills/` 配下 (利用者向け Agent Skills。コード例は本規約ではなく「原則コメントを書かず、やむを得ない最小限のコメントは英語で統一する」という別規約に従う)
- 適用契機: 新規コメントを書くとき・既存コメントに触れる実装をするとき・コードレビューのとき

### 機械検査

検出ロジックは `scripts/comment_policy_rules.py` にあり、次の 2 つの入口が共有する。

- **書き込み前 hook** (`.claude/hooks/comment-policy-check.py`、`Write` / `Edit` / `MultiEdit` の PreToolUse) — 禁止参照を**新しく増やす**書き込みだけを拒否するラチェット方式。書き込み前から在ったコメント行は既存債務として見逃すため、違反を抱えたファイルの編集は巻き添えでは止まらない
- **リポジトリ全体 lint** (`python3 scripts/comment-policy-lint.py`) — 追跡中の全ソースを走査する。`--summary` でファイル単位の件数を表示する

誤検知に当たった行は、行内に `comment-policy:allow` を書き添えれば個別に除外できる。検査そのものが壊れて無音になっていないかは `python3 scripts/comment-policy-lint.py --selftest` で確認する (許容形式を弾かないこと・worktree 配下でも発火することを含めて検証する)。

**lint の検出範囲は本規約より狭い。** 履歴記述と、変更アーティファクト配下のパス参照の一部 (画像・ログ等の非 `.md` 成果物、接頭辞なしの相対形) は検出対象にしていない — 履歴記述は「書き手の作業を語る文」と「実行時の状態を語る文」が、パス参照は change 配下のパスと公開 URL のホストパスが、それぞれ文字列として同型で機械判定できないため (パターンに例外を足すほど誤検出が増える)。これらの類型はレビューと `lessons/impl.md` / `lessons/ui-impl.md` の作業規律が受け持つ。**lint の検出 0 件は本規約への適合の証明にならない** — レビューは規約本文の禁止類型からコメントを判定する。
