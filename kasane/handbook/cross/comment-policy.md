# ソースコメント規約

この文書は Kasane 標準規約の配布物 (正は Kasane リポジトリの `skills/ksn-init/templates/comment-policy.md`)。プロジェクト側では編集せず、直したいことは配布元へ反映して ksn-update で配り直す。

コメント (doc comment / 行コメント / ブロックコメント / `// MARK:` 等の区切りコメントを含む) は、**そのファイルだけを読んでいる人 (人間・エージェント双方)** にとって意味が通ることを最低条件とする。作業文書 (Kasane の change・デルタスペック・レビュー) はアーカイブされて文脈を追えなくなるため、コメントからそれらに依存した参照・記述をしない。

## 許容する外部参照

リポジトリ内のコード識別子 (型名・関数名・ソースファイル名) への参照は外部参照ではなく、自由に書いてよい (grep で到達でき、消えれば同一コミット内で壊れに気づけるため)。それ以外にコメント中で参照してよい外部識別子は以下の4種のみとする。

- **`<domain>/ADR-NNNN`** — `kasane/decisions/<domain>/NNNN-*.md` に確定した設計判断への参照 (例: `cross/ADR-0007`)。ADR は必ずこの ID 形式で書き、ファイルパスでは書かない
- **URL** — 恒常的に到達可能な公開文書 (公式ドキュメント・仕様書・RFC 索引など)。GitHub issue やコミットへの言及も恒常 URL 形式で書く
- **RFC 等の恒常的規格** — `RFC 6749` のような業界標準の識別子
- **他リポジトリのコード識別子** — 互換仕様・対応関係を**現在形の仕様説明**として書く場合に限る (例: 「X 版の `PageModelCore` と同じ責務分担」)。「X から移植した」のような時間軸の記述は禁止する記述類型に従い書かない

## 禁止する参照

以下の外部識別子はコメントに書かない。

- **作業文書のパス** (`kasane/` `openspec/` 配下の `spec.md` `design.md` `proposal.md` 等) — 作業文書はアーカイブされ、指す先の意味を後から追えない。アーカイブされない文書 (concepts / handbook 等) もコメントからはパスで参照せず、設計根拠は ADR の ID 形式に限る
- **変更・フェーズ識別子や文書名の裸参照・行番号参照** (`本提案 add-xxx-core` `delta spec Requirement「〜」` `spec L31-32` 等の、リンクや拡張子を伴わない参照) — 拡張子を書かなくても意味は同一で、grep で検出しづらいだけ。ADR に対応があれば `<domain>/ADR-NNNN` へ置換し、無ければ自己完結する説明に書き直す
- **議論・レビュー・タスクのローカル通番と仮称** (`Phase 18` `Round 2` `Decision 5` `論点 23` `案 β` `Major-1` `review-001` `タスク 2.4` 等) — アーカイブ文書に依存する番号付けで、元文書を追わないと意味が取れない

## 禁止する記述類型

以下の記述はコメントに書かない。

- **進捗ログ・履歴記述** — 「〜で新規追加」「全面刷新」「旧実装を撤去」「〜から移植」「〜へ移行」など、時間軸を含む記述はコメントの仕事ではない (git 履歴の責務): 現在の仕様を現在形で書く
- **アーカイブされた過去仕様の説明** — 「旧 X は〜だった」ではなく、現在の仕様を現在形で書く
- **デルタスペック構文キーワード** (`MUST` `MUST NOT` `SHALL` `SHOULD` `MAY` 等) — 仕様差分文書の記述用キーワードであり、実装コードのコメントには残さない: 規範性は自然な日本語 (「〜する」「〜してはいけない」) で表現し、根拠の参照が必要なら `(<domain>/ADR-NNNN)` を添える

## 公開メンバーの doc コメント

ライブラリ利用者から見える公開メンバー (public な型・メソッド・プロパティ等) の doc コメントには、**内部用語を一切使わない**。ADR ID (許容参照であっても)・change・デルタスペック・Kasane 等、リポジトリの開発運用に由来する語はすべて内部用語である。

- 公開 doc コメントは**機能と契約だけ**を、リポジトリ内部の文脈なしに初見の利用者に伝わる説明で書く
- 設計根拠 (ADR 参照等) を残したい場合は、公開 doc コメントではなく非公開の実装側コメントに置く

事後判定: 公開 doc コメントだけを抜き出して読んだとき、ライブラリの利用方法以外の予備知識なしで意味が通れば適合。

## 書き換え時の判断基準 (3 類型)

既存コメントに禁止パターンが混入している場合、以下のいずれかで書き換える (デルタスペック構文キーワードは自然な日本語への言い換えだけで済む)。

1. **定型句型** (参照が装飾で本文と独立している。例: `// 仕様: <作業文書のパス>`): 参照句を削除し、残る説明が自然に読めるよう整形する。対応 ADR があっても、参照が説明として機能していないなら置換せず削除でよい
2. **理由一体型** (参照タグと設計理由が一体化しており、単純削除すると文意が壊れる): 対応する ADR が `kasane/decisions/` にあれば `<domain>/ADR-NNNN` 参照に置換し、無ければコメント内で自己完結する設計説明に書き直す。**書き換え作業の中では新規 ADR を起票しない** — ADR 化に値すると迷う判断に出会ったら、勝手に起票せずオーナーに確認する
3. **履歴記述型** (過去の仕様を語っている。例: 「旧方式は〜」): 現在の仕様の説明に書き換えるか、情報価値がなければ削除する

## 適用範囲と機械検査

- 対象: リポジトリ内でコメント構文を持つ全ソースファイル (テストコード・サンプルを含む)。対象拡張子の既定と追加・除外ディレクトリは `kasane/config.yaml` の `lint.comment-policy` (`scripts/comment-policy-lint.py` 冒頭に既定の列挙がある)
- 適用契機: 新規コメントを書くとき・既存コメントに触れる実装をするとき・コードレビューのとき

機械検査は `scripts/comment-policy-lint.py` 1 本 (Kasane 標準装備。配布・更新は ksn-update):

- **lint** (`python3 scripts/comment-policy-lint.py`) — 追跡中と未追跡の全対象ソースを走査する。`--summary` でファイル単位の件数、`--advisory` で履歴記述の要確認分も表示する
- **書き込み前 hook** (`--hook`、PreToolUse に登録) — 禁止参照を**新しく増やす**書き込みだけを拒否するラチェット方式。書き込み前から在ったコメント行は既存債務として見逃すため、違反を抱えたファイルの編集は巻き添えでは止まらない。エージェント経由の書き込みにのみ効き、人間がエディタで直接書いたコメントは lint でのみ検出される
- **自己テスト** (`--selftest`) — 検査が壊れて無音になっていないかを確認する (許容形式を弾かないこと・worktree 配下でも発火することを含む)

誤検知に当たった行は、行内に `comment-policy:allow` を書き添えれば個別に除外できる。**検査の検出範囲は本規約より狭い** — 履歴記述・公開 doc コメントの内部用語は文脈依存で機械判定できないため、コードレビューが規約本文から判定する。検出 0 件は適合の証明にならない。
