KsSettingsView のリリースを定型的に実行するためのスキル。

## 手順の正はこのスキルではない

リリース手順の正は次の 1 枚である。

```
kasane/handbook/cross/release-procedure.md
```

**起動のたびに、この文書を先頭から本文まで読む。** 記憶や要約で代用しない。以降の実行は、この文書に書かれた順・書かれたコマンドのとおりに行う。

このスキルは段の順序・節の並び・コマンドを持たない。手順書で節が増えても並びが変わってもコマンドが変わっても、このスキルを直す必要は無い — 手順書を読み直した結果がそのまま実行になる ([cross/ADR-0030](../../../kasane/decisions/cross/0030-release-notes-from-pr-body-and-handbook-as-procedure-source.md))。手順書に書かれていない手順を足さない。手順書の記述と手元の状況が食い違ったら、自分で補間せずユーザーへ返す。

このスキルが自分で持つのは次の 2 つだけである。

1. リリース pull request に書く `## Changes` の下書きを作る手順 (下記)
2. 判断をユーザーへ返す境界 (下記「判断はユーザーが行う」)

## 進め方

1. 手順書を先頭から読む。手順書の「この手順書の使い方」が読む順を示しているので、それに従う
2. 手順書の各段を順に実行する。1 つの段を終えるたびに、その段の**到達状態**を手順書の記述と突き合わせ、達したかどうかをユーザーに示す。達していないまま次の段へ進まない
3. `## Changes` を書く段に来たら、下記の手順で下書きを作ってユーザーに示し、確定した文面を受け取ってから先へ進む
4. 実行が失敗したら、下記「失敗を検出したとき」に従う

各段の報告は次の形で出す。

```
段: <手順書の見出し>
到達状態: 達した / 達していない (<何が足りないか>)
根拠: <実行したコマンドと結果、確認した画面・API の応答>
次にすること: <手順書の次の見出し> / ユーザーの判断待ち (<何を決めてほしいか>)
```

## `## Changes` の下書きを作る

**範囲はこれから作る pull request が `main` へ新しく持ち込む差分だけ** とする。前回のリリース以降の全変更を範囲にしない — 既に `main` へ入った変更は、それを持ち込んだ pull request の `## Changes` が既に持っており、ノートに二重に載る。

```bash
git fetch origin main develop
git log --no-merges --reverse origin/main..origin/develop --pretty=format:'%h %s%n%b%n--'
```

得られた commit を次の規則で下書きに変える。

- **利用者から見える変化だけを載せる。** 公開 API・配布物・利用者向けドキュメントに現れない変更 (ハーネスの整備・CI の調整・内部リファクタ・テストの追加) は載せない
- 1 項目 1 行で `- <種別>: <説明>` の形にする。種別と説明の書式の正は `.github/pull_request_template.md` の「記入の仕方」にあるので、そこを読んで合わせる
- 説明は利用者の言葉で書く。commit メッセージの接頭辞や内部の識別子をそのまま持ち込まない
- 複数 commit が 1 つの利用者向けの変化にまとまるなら 1 項目にまとめる
- 載せるものが 1 つも無ければ、変更なしを示す単独の記載 1 行だけにする

下書きは**下書きのまま**ユーザーに示し、種別の割り当てと文面の確定を委ねる。確定前に pull request 本文へ書き込まない。判断の材料として、除外した commit とその理由も併せて示す。

## 失敗を検出したとき

1. 失敗した位置を特定する (どの job / どの step か、ログのエラー行)
2. 手順書の失敗時の記述のうち、**その位置に対応する箇所**を引用してユーザーに示す。位置に対応する記述が手順書に無ければ「該当なし」と明示する (当てはまりそうな別の記述で埋めない)
3. 再実行するかどうかはユーザーに決めてもらう。勝手に再実行しない

## 判断はユーザーが行う

このスキルは判断を担わない。次はいずれもユーザーが決める。

- 出す version 番号
- `## Changes` の最終的な文面と、どの変更を利用者向けとして載せるか
- 失敗したときに再実行するかどうか、どの再実行の形を採るか
- リリースを中止するかどうか

## Guardrails

- **自発的に起動しない。** 起動・公開は不可逆であり、ユーザーの明示依頼から始める
- **手順書を読まずに実行しない。** 前回の実行の記憶で進めない (手順書が変わっている可能性がある)
- **手順書に無い手順を足さない / 端折らない。** 不足や矛盾に気づいたら実行を止めてユーザーへ報告し、手順書の改訂はユーザーの判断に委ねる (このスキルは手順書を書き換えない)
- **公開を伴う操作をユーザーの確認なしに実行しない** — pull request のマージ、release workflow の起動 (`dry-run` でない実行)、tag の作成
- **確定していない下書きを pull request 本文に書き込まない**
- 削除コマンドは `rm` ではなく `trash` を使う (プロジェクト規約)
