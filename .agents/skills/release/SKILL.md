KsSettingsView のリリースを定型的に実行するためのスキル。

## 手順の正はこのスキルではない

リリース手順の正は次の 1 枚である。

```
kasane/handbook/cross/release-procedure.md
```

**起動のたびに、この文書を先頭から本文まで読む。** 記憶や要約で代用しない。以降の実行は、この文書に書かれた順・書かれたコマンドのとおりに行う。

このスキルは段の順序・節の並び・コマンドを持たない。手順書で節が増えても並びが変わってもコマンドが変わっても、このスキルを直す必要は無い — 手順書を読み直した結果がそのまま実行になる ([cross/ADR-0030](../../../kasane/decisions/cross/0030-release-notes-from-pr-body-and-handbook-as-procedure-source.md))。手順書に書かれていない手順を足さない。手順書の記述と手元の状況が食い違ったら、自分で補間せず止まってユーザーへ返す。

このスキルが自分で持つのは次の 3 つだけである。

1. リリース pull request に書く `## Changes` の下書きを作る手順 (下記)
2. ユーザーに確認する点 (version と `## Changes` の 1 回だけ) と、確認の後を自動で進める範囲 (下記「確認は 1 回、あとは自動」)
3. 自動の進行を止めてユーザーへ返す条件 (下記「止まるとき」)

## 確認は 1 回、あとは自動

ユーザーに確認するのは **version と `## Changes` の文面の 2 つを、1 回のメッセージでまとめて** だけである。それ以外の段ごとの「進めていい?」は聞かない。

1. 手順書を先頭から読む
2. version がユーザーの依頼に含まれていなければ、確認のメッセージで一緒に尋ねる (前回の version と、下書きに breaking があるかを判断材料として添える)
3. 手順書の「1. 事前確認」を実行する (ローカルの `develop` が `origin/develop` より先行していれば push し、その検証 CI の完了を待つ段を含む — 手順書のとおり)。利用者向けドキュメントの追随が要ると判断したら、それも確認のメッセージに添える (docs-refresh はオーナーが依頼するものなので、要否の判断だけを示す)
4. 下記の手順で `## Changes` の下書きを作る
5. **確認のメッセージを 1 回出す**: version (未定なら候補)・`## Changes` の下書き・除外した commit と理由・事前確認の結果 (1 行)。ここで応答を待つ
6. ユーザーが version と文面を確定したら、それを以降の段すべての承認として扱い、手順書の「2. リリース PR」から「5. 公開後の確認」までを止まらずに実行する。pull request の作成とマージ (merge commit)・release workflow の起動 (`dry-run` でない実行)・起動に伴う tag の作成は、この確定で承認済みである
7. 最後に完了報告を 1 回出す (下記「報告」)

### CI の監視

CI の完了を待つ段 (事前確認の検証 CI・リリース PR の 7 件の check・release workflow の run) は、ユーザーに「終わったら教えて」と頼まず、自分で監視する。オーナーは監視を許可している。

- 待ちは background で走らせ、完了の通知を受けてから結果を読む。前面で長時間ブロックしない
  - run が決まっているもの: `gh run watch <run-id> --exit-status --interval 60`
  - リリース PR の check: `gh pr checks <番号> --required --watch --interval 60`
- 完了したら、成功・失敗を job 単位で読み直してから次の段へ進む (watch の終了コードだけで判定しない)
- pull request が conflict していると CI が起動しない。check が 1 件も走らないときは `gh pr view <番号> --json mergeable,mergeStateStatus` を見る

### 報告

段を 1 つ終えるたびに到達状態を手順書の記述と突き合わせる (達していないまま次の段へ進まない)。ただし段ごとにユーザーの応答は求めない。進捗は 1〜2 行で流し、最後に次の形の完了報告をまとめて出す。

```
リリース <version> 完了
- 各段の到達状態: 1〜5 (段ごとに 1 行。根拠となった run / PR / URL)
- 公開物: tag 2 本・Release・3 レジストリ (確認した画面)
- 気になる点: <あれば。無ければ「なし」>
```

## `## Changes` の下書きを作る

**範囲はこれから作る pull request が `main` へ新しく持ち込む差分だけ** とする。前回のリリース以降の全変更を範囲にしない — 既に `main` へ入った変更は、それを持ち込んだ pull request の `## Changes` が既に持っており、ノートに二重に載る。

```bash
git fetch origin main develop
git log --no-merges --reverse origin/main..origin/develop --pretty=format:'%h %s%n%b%n--'
```

得られた commit を次の規則で下書きに変える。

- **利用者から見える変化だけを載せる。** 公開 API・配布物・利用者向けドキュメントに現れない変更 (ハーネスの整備・CI の調整・内部リファクタ・テストの追加) は載せない
- 1 項目 1 行で `- <種別>: <説明>` の形にする。種別と説明の書式の正は `.github/pull_request_template.md` の「記入の仕方」にあるので、そこを読んで合わせる
- 説明は利用者の言葉で書く。commit メッセージの接頭辞や内部の識別子をそのまま持ち込まない
- 複数 commit が 1 つの利用者向けの変化にまとまるなら 1 項目にまとめる
- 載せるものが 1 つも無ければ、変更なしを示す単独の記載 1 行だけにする
- 下書きは手順書にある `render` で組み立てが通ることを確かめてから示す

下書きは**下書きのまま**ユーザーに示し、種別の割り当てと文面の確定を委ねる (確認は上記の 1 回のメッセージで行う)。確定前に pull request 本文へ書き込まない。

## 止まるとき

自動の進行は次のときだけ止まり、ユーザーへ返す。止まるときは、何が起きたか・手順書の該当箇所・選べる対応 (推奨を先頭に) を 1 回のメッセージで示す。

- **検証や実行が失敗したとき** — 事前確認の検証 CI・リリース PR の check・release workflow のいずれか
  1. 失敗した位置を特定する (どの job / どの step か、ログのエラー行)
  2. 手順書の失敗時の記述のうち、**その位置に対応する箇所**を引用する。位置に対応する記述が手順書に無ければ「該当なし」と明示する (当てはまりそうな別の記述で埋めない)
  3. 再実行するか、直してから戻るかはユーザーが決める。自分では再実行しない
- **手順書に書かれていない状況に当たったとき** — 例: 手順書の前提と手元の状態が違う、手順書のコマンドが想定と違う結果を返す。自分で手順を補わない
- **ユーザーの確定した文面・version のままでは進めないと分かったとき** — 例: `render` が落ちる、version の形式が不正

次はいずれもユーザーが決める (自動では決めない)。

- 出す version 番号と `## Changes` の文面 (確認の 1 回で決める)
- 失敗したときに再実行するかどうか、どの再実行の形を採るか
- リリースを中止するかどうか

## Guardrails

- **自発的に起動しない。** 起動・公開は不可逆であり、ユーザーの明示依頼から始める
- **手順書を読まずに実行しない。** 前回の実行の記憶で進めない (手順書が変わっている可能性がある)
- **手順書に無い手順を足さない / 端折らない。** 不足や矛盾に気づいたら実行を止めてユーザーへ報告し、手順書の改訂はユーザーの判断に委ねる (このスキルは手順書を書き換えない)
- **確認の 1 回より前に公開を伴う操作をしない** — pull request のマージ、release workflow の起動 (`dry-run` でない実行)、tag の作成は、version と `## Changes` の確定の後に限る
- **確定していない下書きを pull request 本文に書き込まない**
- 削除コマンドは `rm` ではなく `trash` を使う (プロジェクト規約)
